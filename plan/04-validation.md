## 2. 测试分层与修改原则

- 纯模型：模糊匹配显示、相对时间格式、状态选择、行高与图几何；保持可直接由 Node 导入，不为微小文案变化增加镜像测试。
- Rust 单元：解析、候选集合、时间索引、上下文失效、票据重查、结果归类和有界调度。
- Git fixture：使用真实用户 Git 语义但隔离配置；包含路径特殊字符、工作树/索引/对象库变化，不以 mock Git 代替关键语义。
- UI/桌面：Tauri 中验证输入法、气泡、窗口按钮、外部工具、焦点、重启；浏览器 DOM 通过不能代替原生窗口通过。
- 性能：复用 `tools/bench/` 的进程树及 phase timing，更新旧 UI 探针；`tools/live/` 采图；Linux AT-SPI 证据不推广为其他平台结果。

移除远程产品能力后，远程专用测试按对应代码是否仍存在处理。保留的共享 runner/write/生命周期必须继续测试；被移除的命令增加“不可调用”契约检查。不能让旧 askpass 端到端用例阻止合法清理所有 askpass 实现，也不能为通过本地测试悄悄重新注册网络命令。

### 3.3 mtime 与实时监控

| 场景 | 必须观察到 |
| --- | --- |
| 固定当前时间 19:57、最新 mtime 19:51 | `6m ago`，与最近 commit 时间和打开时间无关 |
| clean 已跟踪文件、未跟踪文件、只有 staged 更改 | 都按候选现存文件 mtime，不只看 dirty 列表 |

| 时钟后退、未来 mtime、休眠恢复 | 无负数或“刚刚修改”伪结果；校准状态明确 |

以下是拟定验收预算，A 阶段记录硬件/基线后可依据测量修订，并在修订记录中解释。不能在未测前把数字写进 README 成为产品承诺。

| 指标 | 暂定目标 | 测量方法 |
| --- | --- | --- |
| 输入到本地候选反馈 | warm p95 ≤150ms；需扫描时 ≤150ms 出加载反馈，首批 p95 ≤500ms（常规夹具） | 记录 input/query/result/render 时间；不把 debounce 隐藏在统计外 |
| 文件变化到状态显示 | 常规夹具事件模式 p95 ≤1s；连续事件 capture 等待 ≤1s 加读取时间 | 真实写入与 UI landmark，记录捕获耗时 |
| 降级 polling | 检测周期目标 5s + 有界读取耗时；大型元数据扫描另标 stale | watcher 失败注入、poll 调度与渲染日志 |
| 首屏可观察 | warm p95 ≤1s，cold p95 ≤2s（常规夹具） | 启动至有效文件/图/活动状态；partial 不算 ready |
| idle CPU | 5 分钟稳定窗口内进程树平均 <1 个逻辑核的 1%；无 Git 周期重查，除显式 polling | 平台进程树采样，记录计时设置和模式 |
| idle 常驻内存 | 同机同夹具不高于基线；**进程树 PSS ≤200MiB**（Linux 常规夹具，≤10k dirty 文件；极大型仓库 >50k 文件 ≤250MiB）。口径为 PSS（共享页按映射进程数分摊），不是 RSS 相加 | WebView 子进程与 Git 子进程纳入；**必须记录 PSS 而非 RSS**，并记录 RSS/PSS 口径差异。修订依据见下方 §4.1 |
| 长时增长 | 30 分钟写入/切换后、缓存稳定时无持续线性增长；结束回落/稳定区间需记录 | timer/listener/query/cache 数量和 RSS 时间序列 |
| 深历史和文件列表 | 10k dirty files / 100k commits 不一次性构建全量 DOM；按 viewport 有界 | DOM 行数、分页耗时、图状态缓存占用 |

常规夹具：1k 已跟踪文件、100 个 dirty、10k commits、少量分支/Tag，另测空仓库、10k 文件、100k commits 和复杂图。每个性能单元至少 20 次 warm 操作统计 p50/p95，启动 cold 与 warm 分开，记录失败/取消样本；长时资源测试单独进行，不用一次耗时声称 p95。

现有 `bench_run.py`/`run_matrix.sh` 依赖 Linux `/proc`、AT-SPI 和旧 UI；先修改定位并验证采样有效。其他平台使用对应进程树工具，不横向比较不同内存口径。与 VS Code 比较若需要，必须同机同仓库同工作负载；不能直接继承旧文档的未经本次复测结论。

### 4.1 idle 内存预算的修订记录（阶段 H，提交 `58b9917` 之后）

初版预算写的是"进程树 RSS ≤150MiB"。这个数字有两个问题，都在这一轮量清楚：

1. **口径错。** 面板是三个进程映射同一份 ~170 MiB 的 GTK/WebKit 库文本。把驻留集（RSS）相加，这份共享代码每个进程数一遍，同一个面板被报成三倍重。按比例集大小（PSS，共享页按映射它的进程数分摊）才是它实际被收取的内存。
2. **没量过地板就定了数。** 150 MiB 这个数是先验写下的，而任何 WebKitGTK 面板的地板都比它高。

同一台宿主、同一 release 构建、同一量法（每种形状取四次采样的最低值，即稳态）：

| 形状 | 进程树 PSS | 相对地板 |
| --- | --- | --- |
| 欢迎页，未开仓库 | **167.3 MiB** ← 地板 | — |
| 10 跟踪文件 | 178.9 MiB | +11.6（每仓库固定：首屏图、路径表、分配器） |
| 1,000 跟踪 + 100 脏 | 179.3 MiB | +12.0 |
| 5,000 跟踪 + 100 未跟踪 + 100 脏 | 183.9 MiB | +16.6 |

由此得到两条可推的结论：
- **规模维度**：斜率约 **1 KiB/跟踪文件**。本文档自己承诺测的"10k dirty files"因此落在 **~177 MiB**；50k 文件的仓库约 **~217 MiB**。
- **时间维度**：1,000 文件夹具空闲 180 秒，私有内存 40.6–47.2 MiB 锯齿（GC 起伏）、无上行漂移，且不随仓库大小增长（guit 自身 10 文件时 200.5 MiB、5,000 文件时 197.5 MiB RSS）。**没有泄漏可修**——错的是量它的尺子，不是被量的东西。

**修订后的预算**：PSS ≤**200 MiB**（常规夹具，≤10k 脏文件），>50k 文件的极大型仓库 ≤**250 MiB**，均以欢迎页地板 167 MiB 为不可压缩的下界。

**对用户体验与基线的影响（预算修订要求随附）**：
- **用户**：一个开着 5,000 文件仓库的常驻面板占约 184 MiB，其中约 45 MiB 是 guit 自己的数据与运行时，约 130 MiB 是 GTK/WebKit 的平台成本。地板那 167 MiB 不随仓库改变，也不由 guit 决定——旧数字把这份平台成本算作面板的超支，是把尺子的问题记成产品的问题。按新预算，一个常规仓库留有 ~20 MiB 余量、一个极大型仓库留有 ~33 MiB。
- **基线**：A02 当时量到的 437.4 MiB RSS 在 PSS 口径下约等于本轮的 167–184 MiB，两者指同一件事。`tools/bench/idle-baseline.py` 已改为读 `smaps_rollup` 并输出 PSS 与私有／共享拆分，RSS 保留只为与历史记录对照。**不再有"超预算 3 倍"这个结论**。

本轮未做平台配置研究去压 WebKit 子进程（那属另一条工作线）；若将来做了，地板会下降，预算应随之重算——**预算跟着地板走，不跟着某个一次性测量走**。

## 5. 执行命令与证据保存

应用代码修改后的正式检查从 `app/` 执行。Node 应使用项目记录的可直接运行 erasable TS 测试的版本；先检查工具链，不把不兼容 Node 的错误当业务回归。

```sh
npm run build
npm run test:fixture
cargo test --manifest-path src-tauri/Cargo.toml
cargo fmt --manifest-path src-tauri/Cargo.toml --check
cargo clippy --manifest-path src-tauri/Cargo.toml --locked --all-targets
python3 ../tools/bench/color-contrast.py dist/assets
python3 ../tools/bench/responsive-check.py src/style.css src/style/tokens.css
npm run bin:release
```

两个 stylesheet gates 必须在 build 后运行。fixture 不替代 tsc。clippy 的历史 warning 要对比基线，不无说明改成更宽松检查。新增依赖若影响 lockfile，记录原因和构建体积。

针对性检查先运行变更模块的现有/新增测试，再满足全套 gate；纯文档更新不需要启动完整桌面构建。桌面运行和 release binary 启动记录另存，不能用 build 成功替代。CI 必须有真实运行链接/日志才记录通过；本次只看到 origin 配置，未核验远端 CI。

证据记录至少含提交号、OS/桌面/WebView/Git/Node/Rust、fixture 种子与规模、构建模式、命令/退出码、时间戳及测试日志位置。避免保存实际用户文件内容、凭据、提交正文或私人路径；截图使用生成夹具。

## 6. 交付门槛与停止条件

必须阻断发布：数据过期却显示成功、错误图连接、无结果却未完成搜索、mtime 伪用事件时间、票据可重用、预览外文件损失、ignored/嵌套仓库被通用清理、远程命令仍能从产品调用、坏主题无法恢复、窗口关闭绕过清理或文件内容进入 DOM。
