## 1. C01：连续事件会饿死刷新（已定位的具体路径）

`app/src-tauri/src/watch.rs` 的 `run_loop` 在 Watch 模式下收到事件后进入内层循环，
每再来一个事件就把 `deadline` 重设为 `now + debounce`（`watch.rs:82-93`）。
只要事件间隔小于 250 ms，`now >= deadline` 永不成立，`fire()` 永不执行：
外部 agent 连续写文件时，guit 停在旧状态，而这正是本产品的主场景。

现有测试覆盖不到它：`watch_events_debounce_into_a_single_fire` 用 20 ms 间隔发 5 个事件后停手，
quiet period 得以走完。缺失的那条断言是“事件永不停时刷新仍发生”。

这条路径的可达性现在有了间隔数值（§1.4 那张表的最后一列）：四种真实写入节奏下，
非 Access 事件的**最大间隔是 22–42 ms**，全部远小于 250 ms。也就是说饿死不需要构建风暴，
一个持续追加日志、下载文件或增量编译输出的进程就足够；那条测试的 5 个事件之所以能 settle，
只是因为发完之后停手了。后来按保存形状补测的那一档更贴近本产品：编辑器原子保存
（写临时文件再 rename）在 40 ms 节奏下最大间隔 0.041 s（§1.4 末那张表），
所以连“用户只是在一个文件上反复按保存”都能饿死刷新。

目标契约（对应设计 §3.2）：

- 从**首个事件**起计最大等待（目标 1 s），到点即触发一次合并捕获，即使仍在收事件；
  250 ms quiet debounce 保留为“事件停止后”的路径，两者取先到者。
- 捕获进行中不启动第二个 Git 读：沿用 `session.rs` 的 leader/rerun 门（`refresh_with`），
  watcher 侧只置重跑标记。
- 事件携带的**种类与路径**必须保留到内部队列，作为“哪个数据域失效”的线索
  （工作树 → 状态 + 文件元数据；HEAD/refs/index → 相应域）。当前实现把事件压成 `()`
  （`watch.rs:158`），因此无法区分这两类，也无法增量更新 mtime。
- 队列有上界；溢出不是“没有变化”，而是合并成一个“需要重新核对”状态（两处上界的形状见 §1.4）。
- 运行时 watcher 错误（创建成功但后续失败、队列溢出、休眠恢复）要产生可见的 stale 降级，
  并允许重建或降级到轮询。`choose_mode` 只覆盖“创建即失败”一条路径（`watch.rs:203`）。
  今天**根本看不见**运行时错误——回调里写的是 `if let Ok(event) = result`
  （`watch.rs:155-160`），`Err` 分支不存在，notify 递回来的错误直接被丢弃；同一处的
  `let _ = events_tx.send(())` 也忽略通道已关。C01 要把这两处变成可判定的输入。
  但实测否定了“把 `Err` 接进队列就算覆盖了运行时降级”这个隐含假设：监听目录被删除时
  notify **不发 `Err`**，而是整条通道归于沉默（§1.2）。降级检测的真实来源因此是
  事件路径、刷新失败与一次有界的静默重建，而不是错误半支。
- 端到端延迟包含 Git 读取耗时，文案不能把 1 s 说成任何仓库都能达到的上限。

一个必须保持的既有事实：`repo::status_output` 带 `--no-optional-locks`，因为它测到
普通 `git status` 会创建并删除 `.git/index.lock`，这些事件回流给 watcher 后一次真实改动
会引发无限刷新（`repo.rs:365-369`，并有测试 `status_output_never_acquires_the_index_lock`）。
新增的元数据读取同样不得取索引锁，也不得自己成为事件源。

### 1.1 保留路径与种类的真实用途（防止按域失效被做成一张矩阵）

快照的容量比“七域客户端”的表象小得多。`SnapshotView` 只有
`repo / branch / files / operation` 四项（`session.rs:175-186`），
`capture_inner` 的全部内容是**一次 `git status` 加一次 `inflight::detect` 文件读**
（`session.rs:200-223`）；分支列表、tag、stash、worktree、history 页都是独立的按需命令
（`main.rs:1232-1245`：`history_page`、`list_refs`、`stash_list`），不在快照里，
也不由 watcher 触发。

因此“事件携带种类与路径”不是为了在后端若干 Git 读之间做选择——后端只有一个捕获单元，
任何非 Access 事件都等价于“重新捕获”。路径的真实用途只有三处，C01/C03 的改动范围
按这三处定，不多做：

1. 判定该事件是否与已捕获状态无关，从而**抑制**无谓刷新（目前唯一的抑制是丢 Access）。
2. 给 C03 的 mtime 索引做**免 Git 读**的增量更新：工作树内的路径直接按项改表，
   不需要 `ls-files`，也不需要 `git status`。
3. 判定**枚举规则来源**是否变化（`.gitignore`、`.git/info/exclude`、`git config` 里的
   `core.excludesFile`），这类事件才需要付一次全量重枚举。

第 2、3 两类是互斥的分流：把 `.gitignore` 的事件当作“改一个文件项”处理会让候选集合
停留在旧忽略规则下，反之把每次保存都升级为全量重枚举，就等于把 §2.2 的 18–22 ms
挂在每个按键上。实现必须显式区分这两类并有各自的测试。

### 1.2 监听失效不可从错误得知（实测），因此 Watch 模式必须自带兜底

一次性原型 `/tmp/guit-c01-proto`（`dead_watch`、`rearm` 两个 bin，`notify =8.2.0`，
与 `app/src-tauri/Cargo.lock` 锁定的版本一致）测出五条形状各异的后果：

1. **被删掉的监听根会彻底沉默。** 监听 `root` 后 `rm -rf root`，回调收到
   `Remove(File)` 若干加一条 `Remove(Folder) ["root"]`；随后 `mkdir` 同名目录再写文件，
   回调**一条事件都没有**（实测 0 条），也没有任何 `Err`。沉默的原因是父目录不在监听
   集合里，根目录自己的重建不会产生事件。因此“把 `Err` 接进队列”不能覆盖这一类失效。
2. **可用的证据只有事件路径。** `Remove(Folder)` 的路径等于 `watch_targets` 的某一项
   （`watch.rs:121`）就是“这个监听根刚消失”的正面证据。这是 §1.1 三处用途之外的
   第四处，也是保留路径唯一无法用“刷新=全量重捕获”替代的理由：环路需要一个时机
   去重建监听，而不是只等下一次用户改动。
3. **重建是安全且幂等的，`unwatch` 不是。** 对同一路径连续调用 `watch(..., Recursive)`
   三次，一次写入仍只产生 4 条事件（`Close(Write)` 恰好 1 条），即 notify 按路径去重，
   不会造成事件翻倍；路径不存在时返回 `Err(PathNotFound)` 而不是 panic，因此可以按心跳
   无条件重发。相反 `unwatch` 对未监听路径返回 `Err(WatchNotFound)`，对内核条目已失效的
   路径返回 `Err(Io(Os { code: 22, kind: InvalidInput }))`，也就是“清理”这一步恰好在
   最需要它的状态下失败；既然重发本身已经足够，就先 unwatch 再 watch 这条写法不要出现。
4. **递归进新目录是异步建立的，中间窗口会丢事件。** 子目录被删除后立刻重建并写入，
   回调只有 `Create(Folder)` 与 `Access(Open)`，新目录里那次写完全丢失；同样场景留到
   500 ms 之后再写则正常。对快照语义无害——触发刷新的那一次 `git status` 会看到一切；
   对 C03 的增量索引有害，见 §3 新增的目录事件规则。
5. **Watch 模式今天没有任何兜底。** `run_loop` 的轮询分支写作
   `if mode == Mode::Poll && Instant::now() >= next_poll`（`watch.rs:104`），
   心跳在 Watch 模式下**永不**触发刷新。结合第 1 条，一个沉默的监听等于一个永不更新的面板，
   而状态栏仍显示 “watch”。因此 C01 的 Watch 分支必须保留一条低频核对
   （复用既有 `poll_interval` 或一个新的显式常量，二者都要在实现说明里点名），
   把“事件驱动”降级为“事件驱动 + 有界兜底”，而不是把 mode 当成二选一。

第 1、5 条合起来是设计 §3.2 那句“降级要可见”的真实内容：可见性不来自 notify 的错误，
而来自环路自己知道“我已经很久没有任何证据了”。测试要钉住的是
“监听根重建后写入重新被看见”与“Watch 模式在无事件时仍会按上界刷新”，
而不是“错误进入队列”——后者对本产品最可能的失效毫无帮助。

### 1.3 Git 自身写入的事件形状（过滤规则的边界，实测）

同一原型的 git 夹具（工作树 + `.git` 双目标监听，等同 `watch_targets`）显示，
一次 `git add` 与 `git commit` 产生 25+ 条事件，其中非 Access 的包括
`index.lock`、`HEAD.lock`、`refs/heads/main.lock`、`packed-refs.lock`、
`AUTO_MERGE.lock`、`maintenance.lock` 的 `Create(File)`/`Modify(Data)`/
`Modify(Name(From|To|Both))`/`Remove(File)`，以及对象子目录的 `Create(Folder)` 与
`tmp_obj_*` 的写。不带 `--no-optional-locks` 的 `git status` 同样产生
`Create(File) ["index.lock"]` 与 `Remove(File) ["index.lock"]`——这就是 §1 末尾
那条自喂回路的来源，已由既有测试钉住。

同一夹具把**反方向**也量了一遍，因为 C01 要新增的两种节奏（最大等待到点的捕获、
§1.2 第 5 条要求的 Watch 模式低频兜底）都会让捕获**变多**，而它们只有在
“一次什么都没改动的捕获不产生任何会触发刷新的事件”成立时才是安全的。
用 `repo::status_output` 的逐字参数
（`--no-optional-locks status --porcelain=v2 -z --branch --untracked-files=all --ignored=no`）、
每次间隔 500–600 ms、共 6 次：

| 仓库状态 | notify 事件总数 | 其中非 Access | 结论 |
| --- | --- | --- | --- |
| 干净、索引 stat 新鲜 | 141 | **0** | 一次无变化的捕获完全沉默 |
| 干净，但把一个已跟踪文件的 mtime 推到未来（索引 stat 缓存过期，正是 Git 最想顺手写索引的那个状态） | 141 | **0** | `--no-optional-locks` 覆盖的正是这一档，不是只覆盖“新鲜”那一档 |
| 同一过期状态，**去掉**该参数 | 174 | **15** = 6 create + 5 remove + 3 modify-name + 1 modify-data | 每次捕获自带一对 `index.lock` 事件 |

前两行是新增节奏的前置条件；第三行是 `repo.rs:365-369` 那次历史测量的现场复现（Git 2.53、
tmpfs，与它记录的同一类文件系统）。顺带量到的一件事：**141 条全是 Access**，
即一次 `git status` 大约触碰 23 个文件，而 `refresh_worthy` 恰好把整类丢掉。
因此本节下面那条“不得把 `Close(Write)` 升格为触发源”的规则，保护的是一个**此刻成立、
改一行就会失效**的性质；C01 若改动过滤规则，上面这张表的前两行就是它必须保住的断言。

另一条必须写进契约的细节：内核的 `IN_CLOSE_WRITE` 在 notify 里是
`Access(Close(Write))`，因此今天 `refresh_worthy` 的 `Access(_)` 整类丢弃
（`watch.rs:146`）**顺带丢掉了“写入完成”这个最精确的信号**。这不是漏洞而是必要的取舍——
git 锁文件的 `Access(Close(Write))` 就在同一批事件里。C01 保留事件种类后不得
“顺手”把 `Close(Write)` 升格为刷新触发源：那会绕过 `--no-optional-locks`
之外的第二道防线，把每次 Git 内部锁写入都变成一次刷新。

### 1.4 有界队列的真实形状：两处上界，溢出只丢细节、不丢“变过”这件事

今天这条通道是**无界**的 `mpsc::channel()`（`watch.rs:214`），载荷 `Sender<()>`
（`watch.rs:151`）。载荷是 `()` 时无界没有代价：每个待处理事件只占一个空元组。
一旦把种类与路径放进载荷，通道本身就变成 §1 想避免的无界内存——消费者在下一次
`fire()` 之前不读它，而 `fire()` 最迟 1 s 才发生一次，所以积压量等于
1 秒内 notify 递来的全部事件。A03 的连续写入夹具正是制造这种积压的。
因此“保留路径”必须先决定放在哪里，这是 C01 唯一还没有实测支撑的形状决定，本文按
现有代码的既有形状定形：

- **通道只送“有事发生”，不送路径。** 改用 `sync_channel(capacity)`，回调里
  `try_send`：`Full` 时**置一个共享的 `AtomicBool` 饱和标志并丢弃这一条**，
  `Disconnected` 是既有的关停路径（今天 `let _ =` 把它和溢出一起吞掉，`watch.rs:158`，
  §1 已要求它变成可判定的输入）。选择 `try_send` 而不是阻塞 `send`，是因为回调运行在
  notify 自己的线程上：阻塞它会背压内核的 inotify 队列，那是比丢细节更糟的失效。
  共享标志沿用环路已有的 `&AtomicBool`（`cancelled`）注入形状，不引入新的锁，
  因此也不接触“绝不 unwrap 中毒锁”那条规则——合并集由单一消费者 `run_loop` 独占，
  不需要锁。
- **路径放在 `run_loop` 一侧的合并集里**，每次 `recv` 后贪心排空通道（`try_recv` 循环），
  把事件折叠成“域失效线索 + 去重路径集”。上界是**去重路径条数**，内存 = 条数 ×
  每条路径字节数，两个因子都显式可命名；键按 §2.4 用字节（`Vec<u8>`），不用 `String`。
  条数上限取“一个 `max_wait` 窗口内真需要逐条增量更新的规模”，超过它本来就该走
  全量重枚举那条更便宜的路。
- **两处的溢出必须是同一个动作：丢掉细节，保留“有变化”这个事实。**
  饱和标志或合并集写满，效果都是把本次窗口的结论降级为“需要一次全量重枚举”
  （即 §1 里那条“需要重新核对”状态），绝不能是“这轮无事”。这条是 fail-closed
  规则在队列上的形态：溢出不是空集。
- 排空时把标志与合并集一起交付，交付后清零；下一次刷新重新建立。
  标志一旦置位，本窗口内不再尝试记录新路径（细节已经不可信，继续只是浪费内存）。

这条形状同时给出 C01 的测试断言：夹具持续投递超过 `capacity` 条事件时，
必须观察到（1）刷新照常发生、（2）结论是“全量重枚举”而不是无变化、
（3）回调线程未被阻塞（用投递侧的耗时上界断言，而不是靠 sleep）。

上面两处上界的**数值**由一次一次性原型测得（同一 crate、debug 构建、`/tmp` 下扁平目录，
每次 `fs::write` 新建一个文件；每窗口先 settle 300 ms 再丢弃注册期间的事件，消费者在窗口内
完全不读，所以记下的就是真实积压）：

| 写入节奏 | 窗口 | 事件总数 | 非 Access | 去重路径 |
| --- | --- | --- | --- | --- |
| 每 50 ms 一次（验收用的连续写入就是这个档） | 1 s | 80 | 40 | 20 |
| 每 50 ms 一次 | 250 ms（quiet debounce） | 20 | 10 | 5 |
| 每 20 ms 一次 | 1 s | 200 | 100 | 50 |
| 每 1 ms 一次（极限突发） | 1 s | 800 | 400 | 200 |

比率在这三种节奏下**完全一致：每次写入 4 条事件、其中 2 条非 Access、1 条去重路径**。
所以两个上界可以直接按“一个窗口内允许多少次写入”来读，而不是凭感觉挑一个条数：
非 Access 条数 = 2 × 写入次数，去重路径数 = 写入次数。取极限突发那一档的 4 倍余量，
`capacity` 落在 2 的 10 次方（1024 条 ≈ 5 s 的验收节奏，或 2.5 s 的极限突发），
合并集的去重路径上限落在同一量级；两个数值都要作为模块内具名常量写下，
理由就是这张表。路径字节数在该夹具里是 35–38 B/条，**不能当作一般值**——单条路径上限
按文件系统走，容量与字节数的乘积才是真实内存上界，这也是不把路径放进通道载荷的第二个理由。

同一原型还测了饱和侧的代价：通道满时 `try_send` 一万次共约 2.7 ms，**平均约 26 ns/次**，
全部返回 `Full`、一次也没有阻塞（`cap=1024` 与 `cap=64` 无差别）。
§1.4 选 `try_send` 而不是阻塞 `send` 因此不是猜测：溢出对 notify 回调线程的额外成本
在噪声级别，而阻塞 `send` 会把背压顶回内核队列。

这张表的适用边界要写清：它是“新建文件的普通写入”的形状。原子保存（写临时文件再 rename）
与 Git 自身写入的事件形状不同——后者已在 §1.3 单独实测（一次 `git add` + `git commit`
25+ 条，含 `Modify(Name)` 对）。实现不得把 4 这条比率当成所有写入的常数，
它支撑的是“上界如何解释”，不是“事件数可以预测”。

那句边界说明里的“另一种形状”现在有了数值，因为它会把这一节的**两个上界解耦**：
反复写同一个已存在的文件（日志、下载、增量编译输出）与新建文件不是同一个换算。
同一类夹具（tmpfs、递归监听仓库根、含 `.git`），最后一列是非 Access 事件之间的最大间隔。
只有“去重路径”那一列是按写入侧的构造给出的（探针按种类计数，不带路径），其余三列是数出来的：

| 负载 | 非 Access 事件 | 每次写入 | 去重路径 | 最大间隔 |
| --- | --- | --- | --- | --- |
| 一个文件每 40 ms 追加一行（每次 fsync），8 s | 201 | ≈1.0 | **1** | 0.042 s |
| 一个文件 400 次 flush × 64 KB，20 ms 间隔 | 395 | ≈1.0 | **1** | 0.022 s |
| 每 40 ms 新建一个文件，8 s | 398 | ≈2.0 | 199 | 0.041 s |
| 全速新建（4 s 内 328,742 个） | 657,484 | 2.0 | 328,742 | 0.003 s |

三条后果：

- **“非 Access = 2 × 写入次数、去重路径 = 写入次数”只对新建文件成立。** 追加负载是
  约 1 条事件、恒定 1 条路径。所以那两个上界不能由同一个“写入次数”换算：
  `capacity = 1024` 在 25 次/秒的追加下要 41 s 才满，而在全速新建下 **6 ms** 就满。
  前者意味着合并集几乎不损失信息（永远一条路径），后者意味着溢出必然发生——
  这两个极端都要落在同一条“溢出=降级为全量重枚举”的规则上，但余量必须按各自的形状给。
- **最大间隔这一列就是 §1 那条饿死的实测依据**：四种节奏全部 22–42 ms 或更小，
  对 250 ms 的 debounce 而言永不 settle。
- **tmpfs 是这对结论里“最不巧”的一侧**：它给出最短的事件间隔，因此饿死结论在慢盘上只会更弱
  （间隔可能偶尔超过 250 ms 而 settle）；反过来，全速新建那一档在慢文件系统上事件率也更低。
  两个数值都是**单主机单文件系统**的量级，不是常数。真正不随文件系统变的结论只有一条：
  一个还在写的进程，其事件间隔没有理由大于 debounce。

那句“实现不得把 4 当成所有写入的常数”里，最重要的那个住户是**编辑器保存**：写一个临时
文件再 `os.replace` 覆盖目标。同一类监听形状（递归、tmpfs、每 40 ms 一次保存、共 60 次），
这一次“事件里的路径”是**数出来的**（夹具内文件名全局唯一，所以路径名条数即路径条数）：

| 保存形状 | 非 Access 事件 | 每次保存 | 事件里的路径条数 | 最大间隔 |
| --- | --- | --- | --- | --- |
| 原地改写一个已存在的文件 | 66 | ≈1.1 | 1 | 0.042 s |
| 同上，但文件放在 6 层深的目录里 | 65 | ≈1.1 | 1 | 0.042 s |
| 原子保存，临时名在 3 个之间轮换 | 300 | **5.0** | 4 | 0.041 s |
| 原子保存，每次一个新临时名 | 300 | **5.0** | **61** | 0.042 s |
| 原子保存 + `utime` 把 mtime 定住（见最后一条） | 120 | **6.0** | 3 | 0.041 s |

四条后果，前两条改数值、后两条改规则：

- **深度不是变量。** 前两行在两种形状下逐项相同（含事件种类分布）。§6 那条“真实仓库的
  目录深度会把突发那一档抬高多少”因此有了答案：**0**。改变比率的是“这次写入有没有换
  一个 inode”，不是它离根多远。
- **一次原子保存固定给 5 条会触发刷新的事件**：`create` 1 + `modify-data` 1 +
  `modify-name` 3（实测恒为 3，是 rename 那一对在 notify 里被拆成的条数）。也就是说一个
  正常按 Ctrl+S 的用户，事件率是“追加日志”那一档的 5 倍，而 §1 那条饿死结论在这一档
  同样成立（最大间隔 0.041 s）。
- **临时名会单独吃掉去重路径那一整个上界。** 每次一个新临时名时，60 次保存留下 61 条
  路径（60 个临时名 + 目标），而**其中 60 条在事件到达时已经不存在**——它们被 rename 走了，
  永远不可能进候选集。按 1024 条那一档换算：1024 次编辑器保存就把合并集写满，代价是
  一次全量重枚举，而真实变化的文件只有一个。于是本节此前没写出的一条规则现在必须写上：
  **合并集不得只进不出**——`Remove` 与 rename 的“源”侧要把该路径从集合里删掉。
  不做这条，那个上界衡量的就不是“一个窗口内需要逐条增量更新的规模”，而是
  “这个窗口里编辑器改过多少次名”，而后者在正常用手上是线性增长的。
- **有事件不等于年龄前进。** 最后一行是先把临时文件的 mtime 用 `utime` 推到过去、
  再 rename 覆盖目标的形状（有些编辑器确实这么做，为了不打断增量构建）：20 次保存给了
  120 条非 Access 事件（每次 6 条，比纯原子保存多的那条是 `modify-meta`），
  而目标的 mtime **0.000 s** 都没动。§3 第一条那句“事件到达时间不得代替 mtime”因此
  有了监听侧的实测出处，并且要读成一句实现规则：**重 `lstat`、写回拿到的值，值不变不是失败**，
  不得因为“算出来和上次一样”就判定这次更新没发生或退化成重枚举。

还有一条接线要求来自验收侧的“手动重试可恢复”：溢出/降级状态必须能被**既有的手动刷新**
清除——`main.rs:110` 的 `refresh_repository` 与 watcher 触发走的是同一条
`session::refresh` → `publish` 路径，复位就挂在发布成功之后。不得为它新增按钮、
新命令或新的前端调用面。

## 2. C02：候选枚举实测契约

候选集合 = Git 认定的“已跟踪文件” + “未被忽略的未跟踪文件”，再按现存文件取最大 mtime。
实测确定的命令与行为：

| 事实 | 实测结果 | 对实现的约束 |
| --- | --- | --- |
| 已跟踪列表 | `git ls-files --cached -z`（含工作树上已被删除、但索引中仍在的文件） | 删除项必须 stat 后跳过，不得当作候选 |
| 未跟踪且非忽略 | `git ls-files --others --exclude-standard -z`；省略 `--exclude-standard` 时忽略规则完全不生效 | 必须带 `--exclude-standard` |
| 普通未跟踪目录 | 默认**递归列出其中的文件**（`newdir/inside.txt`）；加 `--directory` 才折叠成 `newdir/` | 不得使用 `--directory`，否则 stat 到目录本身 |
| 嵌套仓库（未注册，工作区里游离的 `.git` 目录） | `--others` 只输出**目录项** `nested/`，不进入其中（`-z` 输出同样保留斜杠） | 斜杠过滤足以排除这一类 |
| 已提交为 gitlink 的嵌套仓库（索引 mode `160000`） | **`--cached -z` 输出的是不带斜杠的 `nested`**（`ls-files -s` 显示 `160000 <oid> 0<TAB>nested`）。只按斜杠过滤会把它留下，`symlink_metadata` 成功，于是**目录的 mtime 进入候选**；在目录下新建一个文件就会推进这个 mtime，计时被非文件事件污染 | 必须双重排除：`--cached --stage -z` 按 mode 丢弃 `160000`，并在 stat 后丢弃 `is_dir()` 的项。只写其中一条都不算满足本契约 |
| submodule 目录内的游离文件 | `--others` 不进入：Git 自行停在边界 | 不需要额外的“排除 submodule 内容”扫描 |
| 未提交的 `.gitignore` | **照样生效**（`ignored-dir/hidden.txt`、`just-ignored.txt` 被排除）；`.gitignore` 自身作为未跟踪文件出现在候选中 | 候选集合与忽略判定同源，一次枚举即可；无需先提交 |
| `.git/info/exclude` | 生效（`from-info-exclude` 被排除） | 该文件在 `git_dir` 下，已被现有递归 watch 覆盖，不需要新增监听目标 |
| `core.excludesFile` | 生效；值中的 `~` 由 Git 展开，而 `git config --get core.excludesFile` 返回的是**未展开的原文** `~/myignores` | 解析观察目标时必须自行展开 `~`，否则会监听一个不存在的路径 |
| 未设置 `core.excludesFile` 时的默认忽略文件 | `XDG_CONFIG_HOME` 存在时读 `$XDG_CONFIG_HOME/git/ignore`；未设置 `XDG_CONFIG_HOME` 时读 `$HOME/.config/git/ignore`（实测两者互斥，XDG 优先） | 观察目标不止来自配置：默认路径也必须纳入，否则“只改全局忽略文件”这一验收场景失效 |
| 符号链接 | `ls-files --others` 把链接作为单条文件项列出；链接自身的 mtime 与被指向文件的 mtime 相互独立（`utime(follow_symlinks=false)` 只改链接） | 用 `symlink_metadata`（lstat 语义），不跟随到仓库外；据此，外部目标被改写不会反映在活动计时中，属于设计选择而非缺陷 |
| sparse-checkout（cone 模式）目录外的已跟踪文件 | `--cached -z` **照样列出**它们，但磁盘上不存在，`stat` 失败；`--sparse` 标志在 Git 2.53 下对输出无差异；`status --porcelain=v2 -uall` 完全不报它们为删除（10 个文件里 6 个不在盘上，status 只输出分支头） | “已跟踪列表”一行规定的 stat 失败即跳过，天然覆盖 sparse 仓库：不需要识别 skip-worktree 位，也不需要为 sparse 另设候选语义 |

### 2.1 成本量级（同一主机、临时夹具）

| 负载 | 命令 | 实测 |
| --- | --- | --- |
| 10k 未跟踪文件 + 1 条忽略规则 | `ls-files --others --exclude-standard -z`（10001 项） | 6.3 ms |
| 同上仓库（0 已跟踪） | `ls-files --cached -z` | 1.2 ms |
| 同上仓库 | `status --porcelain=v2 -z --untracked-files=all`（10003 项） | 6.4 ms |
| 10k 已跟踪文件仓库 | `ls-files --cached -z` | 2.8 ms |
| 10k 文件逐个 stat（Python `os.walk` 参考实现） | — | 11.8 ms～16.8 ms |
| 10001 项（10k 已提交 + 1 未跟踪）完整“`ls-files` 两次 + 逐项 `symlink_metadata`” | Rust 原型，同一主机 | 中位 18.1 ms，最差 22.0 ms（10 次重建） |
| 同一索引上对最大项取 max（10k 项线性扫描） | Rust 原型 | 约 100 µs/次（“删掉最大项再重建”200 轮共 42.8 ms，含每轮两次扫描） |
| 同一索引上“扫描后写入当前最大项”1000 次 | Rust 原型 | 224 µs/次——几乎全是线性扫描，不是插入 |

最后一行是本阶段最容易被实现掉的约束：**更新路径必须是 O(1)**。把 `max` 缓存在索引上，
一次 stat 得到新 mtime 后只比较“是否 ≥ 缓存的最大值”；只有当前最大项自己消失（被删、
被移出版格集合、mode 变成 gitlink）才付一次线性扫描。若实现写成“每次事件重扫全表”，
10k 文件仓库在持续写入下每事件多付约 100 µs 且随文件数线性增长，
这条代价应当由一个“持续写入下不做全表扫描”的测试固定，而不是靠代码审查。

结论：一次完整“枚举 + stat”在 10k 文件量级实测 18–22 ms（其中 Git 枚举部分 <10 ms），
足以在后台线程做初始扫描，但**绝不能挂在每个计时 tick 上**（设计 §4.2 的“静止时不反复扫描”）。
超过输出上限的枚举按现有 runner 规则失败关闭，不解析截断列表。
本表的“`ls-files` 两次”是当时的命令形状；§3.1 实测同一集合可由**一条组合命令**给出，
实现按那条走，两次调用的成本不再是下界的口径。

### 2.2 枚举输出必须选用的上限

同一夹具（10001 个已跟踪文件，路径平均 13 字节）测得 `ls-files` 的字节量级：

| 形式 | 10k 文件实测 | 与 `runner.rs` 现有常量的关系 |
| --- | --- | --- |
| `--cached -z` | 136,900 B | 超过 `DEFAULT_OUTPUT_LIMIT`（64 KB）约 2.1 倍 |
| `--cached --stage -z` | 636,950 B | 超过默认上限约 9.7 倍，是朴素形式的 4.6 倍 |
| `--others --exclude-standard --stage -z` | 与 stage 形式同量级 | 同上。这一行的读数**含已跟踪项**：`--stage` 会连带输出索引（§3.3） |

按平均路径长度反推，朴素 `-z` 形式在约 **4800 个文件**处就会撞上 64 KB；带 `--stage`
（这里曾记为“C02 排除 gitlink 必需”，该理由已由 §3.3 实测撤回）在约 **1000 个文件**处就会撞上。也就是说：沿用默认上限
会让 guit 在一个中等大小仓库上把活动计时判为 `truncated`。这不是可以“放宽再解析”的
问题——按现有规则截断的列表绝不解析，界面必须如实呈现不可用，而不是空集合或“没有修改”。

这一失败已经有先例可循：submodule 视图读取的 `ls-files --stage` 起初共用 64 KB，
于是约一千个文件以上的仓库就报“列表过大”（包括根本没有 submodule 的仓库），后来改为
在模块内定义具名常量 `GITLINK_OUTPUT_LIMIT = runner::STATUS_OUTPUT_LIMIT`
（`submodules.rs:41`），`docs/known-limitations.md` 记录了这次修正。活动枚举沿用同一形状：
在自己的模块里定义一个具名上限、取 32 MB 档、注释说明它随**文件数**而非提交数增长。
不采用“按条目数截断”，因为 `runner` 的截断按字节判定；超长 UTF-8 深路径同样按字节计。
超过该上限时保持失败关闭，界面按 §4 的 `unavailable` 呈现。

上限触顶时合并形式**少的到底是哪一侧**，本轮补测了（复现见 §7）。夹具：3000 个长度随
序号变化的已跟踪文件 + 3000 个同样变长的未跟踪文件，整条流 107,918 B、平均 18.0 B/条；
把这条流在**每一个**字节位置切断，共 107,917 个切点：

| 观察 | 实测 |
| --- | --- |
| 切在记录中间 | 101,918 个切点 = **94.4%**（上一轮用等长名字测出 0%，那是夹具假象，已在 §7 排除） |
| 丢掉末尾那个不完整字段后能否恢复出干净前缀 | **0 个反例**——任意切点都行，截断不会污染留下的那些记录 |
| 切在 50% 字节处留下的类别 | 保留 3,158 条：**未跟踪 3,000（一条不少）**、已跟踪 158（5%） |

第三行就是 §3.1“未跟踪段在前、已跟踪段在后”那条顺序性质在上限处的后果：一次触顶的
合并枚举**不是两侧各少一点**，而是先吃掉一整侧。而记录里没有类别字段（§3.3），
解析器既看不出少的是哪一类，也看不出少了多少。

所以“截断即不解析”在活动索引上要写成比“别拿截断的捕获去解析”更硬的一条：
**不得把存活的前缀当成一次低置信度的 `partial` 结果**。前缀是被类别偏置过的子集合，
最新那次写入完全可能整段落在被丢掉的一侧；把它当 partial 显示，就是拿“没读到”冒充
“这些是候选”，与 §2.5 要排除的那个形状同源。触顶只有 `unavailable` 一种输出。
顺带回答本文先前挂着的那问（§6）：分开两条命令的截断形状与合并形式**不一致**——
两条各自触顶时失败信号有两个，能知道少的是哪一类，但每一侧被丢的仍是该段路径序的尾部，
仍是任意子集合，同样补不出 `partial`。这个差异不构成改用分开形式的理由。

### 2.3 100k 文件量级：全量扫描仍然够用，上限才是问题

同一主机、同一夹具形态放大到 100000 个已跟踪文件（`dXX/sY/fN.txt`，平均路径约 17 字节）：

| 负载 | 实测 |
| --- | --- |
| `ls-files --cached -z` | 8 ms |
| `ls-files --cached --stage -z` | 17 ms |
| 逐项 `lstat` + 求最大（Python 参考实现，100000 项） | 131 ms；按本轮 Rust 原型 10k 项 18 ms 的斜率外推约 180 ms |
| `--cached --stage -z` 输出字节 | 6,888,900 B（约 32 MB 预算的 1/5） |

两点结论，都影响 C02 的取舍：

1. **partial/stale 不是为了 10 万级仓库而设**。100k 文件的全量“枚举 + stat”在
   200 ms 量级，仍远小于一次轮询兜底周期，一次扫描跑得完。真正需要分批核对、
   保留 partial 的是更大规模、慢文件系统（网络挂载）或磁盘繁忙的情况；
   把 partial 实现成“10 万文件就分块”只会白增复杂度。分批的触发条件应当是
   **实测耗时预算**，不是条目数阈值。
2. **上限先于耗时坏**。stage 形式在 100k 已用掉预算的 1/5，按此斜率约 45–50 万条目
   触顶，届时读取报 `truncated`，活动统计必须进入 `unavailable` 并说明原因
   （§2.2）。这条比耗时更早成为实际约束，也因此 §2.2 的具名上限必须显式选定，
   不能沿用 64 KB。

### 2.4 路径必须是字节；`-z` 不只是分隔符的选择（实测）

一次性夹具里放四个名字：`plain.txt`、`中文.txt`、`quo"te.txt`、
以及一个**非法 UTF-8** 名字 `bad\xff.txt`，实测输出：

| 形态 | 实测结果 | 对实现的约束 |
| --- | --- | --- |
| `ls-files --cached -z` | 原始字节逐字出现：`b a d 377 . t x t \0`，中文名为 `344 270 255 ...` | `-z` 是**唯一不转义**的形态 |
| `ls-files --cached`（无 `-z`） | `"bad\377.txt"`、`"quo\"te.txt"`、`"\344\270\255\346\226\207.txt"` —— C-引用 + 八进制转义 | 合法 UTF-8 的中文名同样被引用（`core.quotePath` 未设置即为真） |
| `status --porcelain=v1 -z` | `?? new\xff.txt\0`，同样原始字节 | 与既有 `repo::status_output` 的形态一致，不必新写解析 |
| 对 lossy 字符串 `stat` | `bad\xff.txt` 经 `String::from_utf8_lossy` 变成 `bad\xef\xbf\xbd.txt`，`stat` 报 `FileNotFoundError` | 见下 |

第三行与第四行合起来是本节的全部理由：**把枚举结果过一遍 `String` 会让该候选静默消失，
不带任何错误。** 如果消失的那一项恰好是最新修改的文件，面板只是显示一个偏旧的年龄——
这是“读失败伪装成正常状态”的同一类缺陷，只是方向相反（伪装成“索引完整”）。
因此契约写死三条：

1. 候选集合在 `activity.rs` 内部以**字节 / `OsStr`** 形态存活，`stat` 走字节路径。
   既有先例够用：`status.rs` 把路径存成 `Vec<u8>`（`raw_path()`），
   `PathTable` 按原始字节映射回 `FileId`（AGENTS.md 的“不能逆向的显示名”规则）。
2. lossy 只允许出现在**显示名**上，先例是 `model.rs:203` 与 `repo.rs:336 to_display`；
   `ActivityView` 的可选显示名因此同样不可逆，不得被前端拿去寻址。
3. §2.2 的输出上限必须以 `-z` 的原始字节计。引用形态把每个非 ASCII 字节从 1 字节
   变成 4 字节（`\344`）再加首尾引号：实测 `中文.txt` 从 10 字节变 18 字节。
   用那种形态估阈值会让上限提前触警。

Git 按字节序输出（`bad\xff` < `plain` < `quo"te` < `中文`），而最大 mtime 与输出顺序
无关，所以取最大必须逐项比较，不得依赖“列表最后一项是最新的”这类巧合。

### 2.5 Git 读不动目录时返回 rc=0 与空结果（实测），状态映射必须按 stderr 分

`status` 与 `ls-files` 在遇到**无法打开的目录**时不改退出码，只在 stderr 上留话。
夹具：`sub/` 里有一个已跟踪且已修改的文件加一个新文件，`ok/` 里有一个新文件，
然后 `chmod 000 sub`。用 guit 实际下发的那条形
（`status --porcelain=v2 -z --branch --untracked-files=all --ignored=no`，
`repo.rs:373-383`）实测：

| 读取 | 退出码 | stdout | stderr |
| --- | --- | --- | --- |
| shipped 的 `status` 形 | **0** | 只有 `# branch.oid`、`# branch.head` 与 `? ok/brand-new.txt`；`sub/deep.txt` 的修改与它旁边的新文件都不出现 | `sub/deep.txt: Permission denied`、`warning: could not open directory 'sub/': Permission denied` |
| `ls-files --others --exclude-standard -z` | **0** | 只有 `ok/brand-new.txt` | 同一条 `could not open directory` |
| `ls-files --cached -z` | 0 | 三项全在，含 `sub/deep.txt` | 空 |

三条结论：

1. **可分辨的状态只能靠 stderr。** 好消息是部分数据真的可用（`ok/` 照样报出），
   坏消息是 `repo::status_output` 现在只 gate 退出码与截断，然后
   `Ok(output.stdout)` 把 stderr 丢掉（`repo.rs:387-407`）。照这个 helper 原样复用，
   活动索引会进入 `ready`，而面板对 `sub/` 的判断来自一次根本没读到的读取。
   C02 因此需要 helper 交出 stderr（或一个“有警告”的标志）。这是 §1.1 之外第二处
   “阶段 C 必须改既有后端形状”的地方，而且改的是**共享**路径：同一个洞今天就让
   快照可以把读不动的仓库显示成“无变化”。修它属于 C02 的前提，不是可选清理。
2. **`stat` 的错误码要分流，不能一律当作“文件不存在”。** §2 的“stat 失败即跳过”
   是为已跟踪但被删掉的文件写的。实测 `sub/deep.txt` 的 `stat` 失败是
   `PermissionDenied`（而 `sub` 目录本身的 `stat` 成功）：文件在，只是 mtime 看不见。
   所以 `NotFound` → 不是候选；`PermissionDenied` 及其它 errno → 候选仍在但
   mtime 未知，本次枚举进入 `partial`。把后者并进前者，正好在最像“索引完整”的时刻
   少算最新的那个文件。
3. **`empty` 与“读失败”是两件事，且 `empty` 可以合法到达。** 新建仓库、从未
   `git add` 过时：`ls-files --cached` 返回 rc=0 且**空输出**，同时
   `ls-files --others` 正常列出文件、`status` 正常报 `?? a.txt`。
   “已跟踪集为空”因此不是错误信号，不得用它推断不可用。真正不可用的形状是 rc≠0：
   `.git/objects` 被 `chmod 000` 后 `status` 与两个 `ls-files` 全部返回 **128**，
   stderr 是 `fatal: not a git repository`——Git 认不出仓库，而不是读不出内容，
   这一支现有代码已经走 `git_status_failed`，是正确的一侧。

据此把状态映射钉成一张表，实现按它写，不按“stdout 是否为空”写：

- `ready`：rc=0 且 stderr 空。
- `partial`：rc=0 且 stderr 非空——可以给出已覆盖部分的 `latestModifiedAt`，
  但必须显示为不完整；这种状态下不得说“无变化”。
- `unavailable`：rc≠0，或输出触及 §2.2 上限被截断。
- `empty`：属于 `ready` 且候选集确实为空（全新仓库就是这条的真实来源）。
- `stale`：与单次枚举结果无关，由 §4.4 第 3 条的单调钟判定。

### 2.6 stderr 只能判空，不能读文本；shared helper 的影响面是两个生产调用点

补测四件事，其中两件事收窄了 §2.5 的结论。

| 形状 | 退出码 | stdout | stderr |
| --- | --- | --- | --- |
| 同一个 `chmod 000 sub` 夹具，`LC_ALL=C` | 0 | 与默认语言同（75 B） | 90 B：`sub/in.txt: Permission denied`、`warning: could not open directory 'sub/': Permission denied` |
| 同一条命令，默认语言（zh_CN） | 0 | 同 | 79 B：**同样两行，但文本是中文** |
| 单个已跟踪文件 `chmod 000`（目录可读） | 0 | `1 .M N... ...`（该文件报为已修改） | **空** |
| `.git/index` `chmod 000` | **128** | 空 | `fatal: ... 打开索引文件失败` |

由此得到三条实现规则：

1. **分类只看 stderr 是否为空，不看文本。** 同一个失败的 stderr 在 zh_CN 下 79 B、
   在 `LC_ALL=C` 下 90 B，文本随 `LC_*`/gettext 变化。补一条边界：
   `user_git_command`（`repo.rs:31-45`）**已无条件**设 `LC_ALL=C`，所以 shipped 路径
   拿到的永远是那 90 B 的 C 文案，zh_CN 那一读是“环境默认下会看到什么”的对照，
   不是 guit 的现场。规则本身不因这个放宽，反而更硬：文案仍然是 Git 的输出，
   随 Git 版本变，而 guit 这边连语言都不控制。任何“按 `warning:` 前缀过滤”
   “从 stderr 里抠出读不到的目录名”都会随语言环境失效——而且实测第一行本来就
   **没有** `warning:` 前缀（它是 git 在 diff-index 阶段写的裸行）。所以
   `partial` 的判据是 rc=0 ∧ stderr 非空，需要告诉用户“哪一部分没读到”时，
   由 C02 自己的枚举给出（§2.5 第 2 条的 `stat` 分流），不从 stderr 反解。
2. **文件级不可读不是读取失败，`partial` 只描述目录遍历。** 已跟踪文件
   `chmod 000` 后 status 仍 rc=0 且 stderr 为空，并把该文件报成 `.M`（模式变化）：
   `stat` 只需要父目录可执行，不需要文件可读。mtime 索引同理能拿到该文件的 mtime。
   因此不得把“内容读不出”算进 `partial`，否则每个正常仓库里被 `chmod 000` 过的
   文件都会让面板长期挂着不完整——那是把 §2.5 想避免的“误报干净”换成了“误报残缺”。
3. **索引损坏那一支已经在正确的一侧，无需为它加分支。** `.git/index` 不可读返回
   128 而非 0，走现有 `git_status_failed`；§2.5 第 3 条的 `unavailable` 覆盖它。

helper 改动的影响面实测清点：`repo::status_output`（`repo.rs:356`）的非测试调用点只有两个
——`session.rs:205`（快照 capture）与 `write.rs:885`（写前 recheck）。两处今天都在丢 stderr，
所以两处都会把“目录读不动”当成“读完了”：快照把不可读目录显示成无变化，recheck 把同一个
不完整集合当成绑定事实去确认。签名因此从 `Result<Vec<u8>, ProbeError>` 改为同时交出 stderr
是**两个调用点各自要决定如何使用它**的改动，而不是一个内部重构；C02 的实现提交要么同时给出
两侧的处置，要么把快照那侧的处置记为同批修复，不能只改活动索引一侧就宣称 false-clean 已闭合。
`runner::Output` 本来就带 `stderr: Vec<u8>`（`runner.rs:20`），所以这次改动不触碰 runner 缝隙。

## 3. C03：增量更新的触发来源

“哪些来源变化会改变候选集合”已由上表给出，落到监听上需要分别处理：

- 工作树内的创建/修改/删除/重命名：事件路径给出线索后按项更新；删除当前最大项后重算次大值，
  允许显示的“多久以前”变大。事件到达时间不得代替 mtime（A03 已用夹具钉住
  “保留旧 mtime 的写入不改 mtime 但使 Git 报脏”；本轮从监听侧补测了同一形状的数值：
  把 mtime 定住的原子保存每次给 6 条会触发刷新的事件，而目标的 mtime 一动不动，§1.4 末）。
- **目录级事件不是项级事件。** §1.2 第 4 条实测：新建子目录里的第一次写入可以完全不被
  看见，因为 notify 的递归覆盖是在处理 `Create(Folder)` 之后才建立的。因此
  `Create(Folder)` 只能解释为“该子树需要一次局部重枚举”（候选集合可能多了整批文件），
  `Remove(Folder)` 只能解释为“该子树的全部条目作废”（可能一次去掉当前最大项）。
  把二者按单条路径增删索引，会让索引长期多算或少算，且正好在批量写入的主场景里发生。
  子树重枚举的边界是 Git 的忽略规则：目录内被忽略的文件不得进入候选，
  所以这条路径仍需 §2 的 `ls-files` 语义。范围能不能缩到该目录、缩了能省多少，
  由 §3.1 实测回答，结论是**不缩**。
- `.gitignore`（含各子目录）、`.git/info/exclude`：位于已监听目录内，事件可得，触发候选重枚举。
- 全局 `core.excludesFile` 与 XDG/`$HOME/.config/git/ignore` 默认路径：**在仓库之外**，
  现有 `watch_targets` 不覆盖。这里定为**不引入任何仓库外的监听目标**，改为有界低频
  的 metadata 核对（对解析后的那一个路径比 `mtime`+`size`），理由有三条，前两条实测：
  1. 监听父目录的代价不可控。当 `core.excludesFile` 指向 `~/.gitignore_global` 时它的
     父目录就是 `$HOME`；本主机 `$HOME` 仅前两层就有 515 个目录，而 notify 的递归是按
     目录逐个申请 inotify watch（`fs.inotify.max_user_watches` 本机 65536，
     **每用户共享**，guit 自己的仓库监听也花这同一份预算）。为了少等一次全局忽略的变更，
     把面板的 watch 预算押在用户主目录的规模上，不成比例。
  2. 该路径常常不存在，而“不存在”正是 §1.2 测过的静默形状：`watch()` 对缺失路径返回
     `Err(PathNotFound)`，之后它被创建也不会自己回来；另外 inode 语义下编辑器替换文件
     （写新 inode 再 rename）会使针对旧 inode 的监听失效。低频核对同时绕过这两个坑。
  3. 忽略来源变化的后果只是“候选集合需要重枚举”，而重枚举本来就在快照里做。核对晚了
     只会让统计进入 `stale`（§2.5 最后一条），不会让面板说错一个具体的时间。
  核对的节拍**复用 §1.2 第 5 条为 Watch 模式新增的那个有界兜底 tick**，不新增第三个间隔：
  同一次兜底既确认监听还活着，又重看这一个外部路径。路径不可读（`PermissionDenied`）→
  本次枚举进入 `partial`；路径不存在 → 不是失败，就是“无全局忽略”，不得据此降级。
  只有在核对发现该路径本身变了时，才重新解析 Git 配置（`config --show-origin` 一次）。
  核对本身是一次 `stat`，**不发 Git 命令**——这正是验收那条“idle 不常驻执行 Git”要求的形状：
  空闲时的周期成本是一个路径的 metadata 读，不是一次 Git 进程。
- 索引/HEAD 移动、worktree 切换：改变候选集合，需重枚举；`.git` 内部元数据变化
  可触发 Git 状态刷新，但**不得计入 mtime 统计**。

### 3.1 重枚举的命令形状：一条组合命令，且不带路径范围（实测）

上一节的每一条“重枚举”都落到同一次扫描上。本轮把它的命令形状测清楚，结论有两处
推翻本文之前的写法：枚举只需**一次**进程调用，而**路径范围不值得加**。
夹具：50 个目录 × 1000 个已跟踪文件（含一次提交里的 `.gitignore` 与夹具配置文件，
`--cached -z` 共 50,002 项）+ 每目录 40 个未跟踪文件（2,000 项）+
一个被已提交的 `.gitignore` 隐藏的 1000 项目录；同一主机、同一进程内 best-of-7。

| 事实 | 实测 | 对实现的约束 |
| --- | --- | --- |
| 组合命令就是并集 | `ls-files --cached --others --exclude-standard -z` 输出 52,007 项，与“分别跑 `--cached -z` 和 `--others --exclude-standard -z` 再取并集”**逐项相同**，两个集合交集为空，被忽略目录里的 1000 项不出现在任何一种形式里 | §2 表里那两行命令合成一条：一次重枚举 = 一个 Git 进程，不是两个 |
| 组合输出是两段，不是全局有序 | 未跟踪段在前、已跟踪段在后，各段内部字节有序，整体 `!= sorted`（小夹具类别序列 `oooccccc`；50k 夹具整条流恰好 1 次类别切换） | 不得按“先读 cached 再读 others”分段解析这条流，也不得假定它是排好序的整体。它是一个**无类别的集合**，逐项 stat 后取 max |
| 范围对已跟踪那一侧几乎不省 | full 5.3 ms → 限定 1 个目录 4.5 ms → 限定 1 个文件 3.9 ms | 索引读取本身占大头；子树重枚举在 `--cached` 侧省不出预算 |
| 范围对未跟踪那一侧省得多 | full 14.2 ms → 限定 1 个目录 4.6 ms | 范围唯一能省的是未跟踪目录树遍历 |
| 全新目录在范围下可见 | 建 `newdir/` 放 5 个文件后：未跟踪 2,000 → 2,005，`newdir/n0.txt…n4.txt` **逐条列出**；加 `--directory` 才折叠成 1 项 `newdir/` | 印证 §2 表里“不得使用 `--directory`”。`Create(Folder)` 之后这个子树确实枚举得到 |
| 在目录内跑会换一种路径 | `git -C d00 ls-files --others …` 给 `u000.txt`；同一条加 `--full-name` 给 `d00/u000.txt` | 索引键必须是仓库相对的字节路径：范围枚举要么从仓库根跑，要么显式 `--full-name`，二者不可混用 |
| **写错的范围静默返回空** | pathspec `d0`（不是任何真实路径）返回 **0 项**、rc=0、stderr 空 | §2.5 的“空输出 + rc=0 看起来像干净”正是这条路径上的失败形状。范围字符串一旦来自拼接，就不是一个可以靠输出发现错误入参的命令 |

因此本轮定形的重枚举形状只有一条：**不带 pathspec 的 `ls-files --cached --others
--exclude-standard -z`，从仓库根跑，输出当作无类别的字节路径集合**。
这条形状在仅本地收敛之后仍然成立，且不需要重测那张表：`repo::user_git_command` 现在
无条件带上 `-c submodule.recurse=false` 与 `GIT_NO_LAZY_FETCH=1`（后者必须在剥离
`GIT_*` 之后设置，否则会被自己删掉），枚举与快照都经它下发。在一个含 gitlink
（`update-index --add --cacheinfo 160000,…`）与手工搭出的真 submodule（`.gitmodules`
加内部未跟踪文件）的夹具上比对四种下发——默认、只带 recurse、只带 `GIT_NO_LAZY_FETCH`、
两者都带（即 guit 的实际形状）：合并 `ls-files` 的输出**逐字节相同**（45 B、5 项），
“合并 = 两次调用的并集”在四种下发下都成立，`status --porcelain=v2 -z` 同样逐字节相同。
两条控制都不改变本地读取的输出，只改变会下载的那几种，因此 §3.1 的数值与 §3.2 的
九形状比对对它们都还有效。
本节第 2 条 bullet 里“范围可以缩到该目录”的那个方案被否掉，理由不是慢
（限定目录确实把 14.2 ms 压到 4.6 ms），而是三条合起来的性价比：

1. 环路侧的合并（§1.4）已把连续写入压到每窗口一次枚举，全量 15 ms 与范围 5 ms 的差
   不足以换掉一条命令形状；§2.3 的 100k 量级才是需要靠范围或分批解决的那一档，
   而那需要先有实测的耗时预算触发条件（§6）。
2. 范围把“事件字节路径”变成了 Git 的输入。拼接出来的路径写错时（少一层、多一层、
   用了事件里的绝对路径而没转成仓库相对字节），命令不报错、只给空集合，
   于是索引被静默清空。不带范围的同一条命令不可能出现这个形状：**它只会因为
   rc/stderr 而失败**，即 §2.5 已经定形的那一支。
3. 子树范围省不掉“最大项被删后要重算全表”的那一步（§2.1 的 O(1) 约束），
   因为它只影响一次枚举的输入集合，不影响索引结构。

这条结论同时改写了 §2.1 里“两次 `ls-files`”的成本口径：那一行测的是**当时的形状**，
数值仍然有效；实现应发一次组合命令，其同夹具实测为 14.9 ms（52,002 项），
即两个进程合成一个。

### 3.2 边界形状不改变这条结论，但改变了候选集的元素类型（实测）

§3.1 那句“一致性不随命令合并自动传递”当时是未决的，现在测了。
方法：每种形状各建一个 /tmp 仓库（脚本退出即删），分别跑
`ls-files --cached -z`、`ls-files --others --exclude-standard -z` 与合并形式，
按**字节路径集合**比对（不比顺序）。九种形状全部相等：

| 形状 | `--cached` | `--others` | 合并 | 相等 |
| --- | --- | --- | --- | --- |
| 普通目录 + 已提交的忽略规则 + 未跟踪文件 | 4 | 1 | 5 | 是 |
| 一次提交都没有（空索引） | 0 | 1 | 1 | 是 |
| 嵌套仓库且**未**加入索引 | 1 | 3 | 4 | 是 |
| 同一目录已加入索引（mode `160000` gitlink） | 2 | 2 | 4 | 是 |
| 真 submodule（`.gitmodules` + 内部有未跟踪文件） | 3 | 1 | 4 | 是 |
| sparse-checkout：已跟踪但盘上没有 | 3 | 0 | 3 | 是 |
| 名字含非法 UTF-8、空格、换行、Tab、行首 `-` | 3 | 3 | 6 | 是 |
| 暂存的删除 + 一个未跟踪子目录 | 1 | 1 | 2 | 是 |
| 全新的未跟踪目录 | 1 | 5 | 6 | 是 |

合并流的类别切换在九种形状里都**最多一次**（未跟踪段在前那一性质没有因为边界形状而松动），
但 §3.1 已经定形“按无类别集合处理”，所以这一点不需要被实现依赖。

真正新出现的事实是**候选集的元素类型**，它比相等本身重要：

- 普通的未跟踪目录列出的是**叶子**（`fresh/f0.txt`…），
  而含 `.git` 的目录列出的是**一个以 `/` 结尾的目录项**（实测形状 `inner/`）。
  同一条命令的输出里因此混着两种东西：文件路径，和不是文件的目录路径。
- 同一个目录被 `git add` 之后，它在 `--cached` 里是 `inner`——**没有尾斜杠**、
  mode `160000`，同样不是文件。也就是说同一个目录在“未加入/已加入”两种状态下
  连字节路径都不一样，而两种都不能用 mtime 当“最后修改”。
- 再往那个子仓库里写一个未跟踪文件，合并输出**一项都不多**
  （实测：加了 `inner/loose.txt` 之后集合仍是 `[inner, top.txt]`）。
- 目录项的 mtime 实测**不跟随内容**（另一个同形状夹具，目录名 `nested`）：
  原地改写目录里的文件，目录 mtime 不动；往目录里新增一个条目，目录 mtime 才动。
  把目录项当候选文件，结果是一个双向都错的数——
  既漏掉真正的编辑，又把“目录清单变过”当成“某个文件被改过”。
- 子仓库**内部**的文件在两种形式里都看不见（Git 不进入别人的 `.git`）。
  因此活动索引天然不覆盖 submodule/nested 仓库内部，这与 `git status` 一致，
  所以文件列表和那一行年龄不会互相打脸；但它是需要写进 `docs/known-limitations.md`
  的一条范围声明，不是实现细节。
- sparse-checkout 那三项在 `--cached` 里、不在 `--others` 里（不会被双重计入），
  而 `stat` 对它们必然失败。这是**正常状态**而不是读失败，必须与 §2.5 那一支分开：
  `ENOENT`（或没有该文件）是“这项不是候选”，`EACCES`/`EIO` 才是“读不动”，
  后者才进 `partial`。两者都算“全表重算里的一次跳过”的话，
  一个用了 sparse-checkout 的仓库会被永久显示成部分结果。
- 非法 UTF-8、换行、Tab、行首 `-` 的名字在合并形式里逐字节一致，
  §2.4 的字节契约因此对这一条命令成立（不再只是分开形式的结论）。

仓库外的忽略源单独测了六次读数，每次都比对合并形式与分开形式（全部相等）：

| 读数 | 观察到的事 |
| --- | --- |
| 全局 `core.excludesFile` 有 `*.gen`，工作树里两个文件匹配 | 两种形式都不列出它们 |
| 把全局文件**改成** `!*.gen`（同一仓库、不重跑 init） | 下一**次枚举**就重新出现，不需要任何监听或重启 |
| `.git/info/exclude` 追加一个只被它匹配的名字 | 该名字消失，全局源匹配的那个不受影响（两个源各自独立生效） |
| 根 `.gitignore` 自身是未跟踪文件 | 规则生效（它匹配的文件消失），而 `.gitignore` 自己作为一个未跟踪候选被列出 |
| 嵌套的 `sub/.gitignore`（未跟踪）匹配 `sub/deep.gen` | 该文件消失，同目录的 `sub/plain.txt` 仍在（嵌套忽略文件生效，且是从盘上读、不是从索引读） |
| `cache/` 被 `info/exclude` 忽略且目录里有文件 | 整目录内容一项都不出现（合并形式没有把它们补回来） |

这里要**明确更正一次先前的记录**：早先那轮“被忽略的目录”测量里
`sub/.gitignore` 其实从未创建，那条数已被排除（§7 末尾）。本轮的第四、五行
是先建文件再确认它出现在输出里，才作为“忽略生效”的证据引用。

由 §3.1 加 §3.2，C02 的命令形状与过滤规则现在可以一次定死：

1. 枚举仍是**一条不带 pathspec 的** `ls-files --cached --others --exclude-standard -z`，
   从仓库根跑，输出当无类别字节路径集合。
2. 候选 = 其中**确实是普通文件**的项，判据**只有 `lstat`**（它本来就要做，因为要拿 mtime）。
   这里原先还留着一条“按尾斜杠 / gitlink 前缀先剔掉”的分支，已被 §3.3 撤掉：未跟踪项
   根本没有 mode 字段可读，而“按记录形状分类”在他人命名的仓库上不成立。
   **任何情况下都不得**因为剔不掉就把目录项计入统计。
3. `lstat` 结果分流：`ENOENT` → 跳过（sparse/已删未暂存），
   `EACCES`/`EIO`/其它 → 记为读不动，走 §2.5 的 `partial` 与 stderr 判空那一条。
4. 子仓库内部不覆盖，作为范围声明写进限制记录，与 `git status` 的口径同源。
5. 输出触到上限时只有 `unavailable`：存活的前缀是按类别偏置过的子集合（§2.2 末），
   不得当作 `partial`，也不得“先算着手头这些”。

### 3.3 为什么这条命令不带 `--stage`（实测，并更正 §2.2 与上面第 2 条各一处理由）

§2.2 曾把 `--stage` 写成“C02 排除 gitlink 必需”，上面第 2 条也留了一个“按尾斜杠 / gitlink
规则先剔掉”的分支。本轮测出三条后果，合起来把这条理由**撤回**：`--stage` 不但省不掉
`lstat`，还会改变命令的**范围**和**语法**。夹具：一个已跟踪文件 + 两个未跟踪文件
（其中一个的名字故意造成下面第 3 条的形状），同一进程内比对逐字节输出。

| 观察 | 实测 |
| --- | --- |
| `--stage` 会**顺带把已跟踪那一侧拉进来** | `ls-files --others --exclude-standard --stage -z` 与 `ls-files --cached --others --exclude-standard --stage -z` **逐字节相同**；去掉 `--stage` 后两者立刻不同（2 条 vs 3 条）。也就是说一个想“只要未跟踪 + mode”的调用，实际拿到的是整个索引，字节量按 §2.2 的表再乘约 4.6 |
| 未跟踪项**即使加了 `--stage` 也是裸路径** | 同一条输出里已跟踪项是 `100644 <oid> 0\treal.txt`，未跟踪项是 `plain_untracked.txt`。**一条流里两种语法** |
| 语法不能当类别用 | 存在一个合法文件名 `100644 0000000000000000000000000000000000000000 0<TAB>forged.txt`（TAB 是合法文件名字节）。它作为**未跟踪**项出现在流里，形态与一条真实的已跟踪记录**逐字节不可区分**；按“有没有 mode 前缀”分类的实现会把它判成已跟踪。OID 是不是全零也救不了这条：真实未跟踪项根本没有 OID |
| 对比：`status` 的语法是**安全的** | 同一个文件在 `status --porcelain=v2 -z` 里是 `? <name>` —— 前缀标的是**类别**，不是可被文件名伪造的 mode。§2.5 让活动枚举复用 status 那套 helper 的判状态形状，这条差异因此是有意选择，不是巧合 |

因此第 1 条的命令形状**不加 `--stage`**，第 2 条只剩一种做法：

- 剔除非文件项**只能靠 `lstat`**（它本来就要为 mtime 做一次）。“尾斜杠/gitlink 前缀”那条
  分支删除：未跟踪侧没有 mode 可读，而“按前缀形状分类”在他人命名的仓库上是**不成立的**，
  不是“偶尔不成立”。
- 反向的收益也记下来：不带 `--stage` 时每条记录约 13.7 B，带它是约 63.7 B（两个数都取自
  §2.2 那张同夹具表），所以 §2.2 那个 32 MB 档换算成条目数的触顶规模，因这条决定放宽约 4.6 倍。
- 已跟踪侧的 gitlink（`160000`）仍然可以按 mode 剔，但那是一个**只覆盖一半**的优化，
  而它换来的分支正是上面那条不成立的分类法。C02 不实现它。

机制层面的诚实说法：`--stage` 为何连带输出索引，本轮**没有从文档确认**（man 页的该条正文
未被本次抓取到），只记观测到的逐字节相等。实现不得依赖“它一定等价于加了 `--cached`”，
也不得依赖反方向；命令形状按第 1 条逐字写死即可避开这个问题。

## 4. C04/C05 的接口约束（依据现状代码）

- 后端已有单调 `version`（`session.rs::publish`）与只在本快照内有效的 `FileId`；
  `state.ts::applySnapshot` 镜像同一规则。mtime 统计的有效性键必须是
  `sessionId + activityGeneration`（设计 §3.1），因此 C04 依赖 B05 的会话标识先行落地。
- `state.ts` 的通知只有 `"status" | "render"` 两档（`state.ts:150-170`，双 Tab 收敛后仍如此）。
  计时文本每 tick 全量 render 与设计 §3.2“普通计时 tick 只更新文本”冲突；
  需要按域通知。**B03 交出的形状是“按快照字段的内容键分域”，而 §4.6 定形活动不接进
  那套域**（活动不是快照字段），只与它共用 release 登记和“身份要在键里”这条规则，
  不新增第三个全局档位。
- `WatchStatus` 目前只带 `mode` 与 `failed` 两个字段（`watch.rs:168-173`）。
  C01 的“需要重新核对/降级原因”要扩展这个事件体，前端 `watchStatus()` 同步跟进；
  文案属于 shipped text，不得出现阶段编号。
- 间隔 `x`：默认 5、整数 1–60，只控制文本重算；非法值拒绝并保留原值，
  且同一时刻只允许一个计时器（C05）。持久化位置与它为什么不属于后端见 §4.1。
  这一读法直接锚定在产品权威上：大纲的偏好表把 `x` 写成
  “用于计时显示，不替代 Git 状态监听”，正文写成“计时文字按间隔重算，
  文件变化触发数据更新，静止时不能为更新文字而反复执行 Git 或全目录扫描”。

### 4.1 设置值只控制文本重算，因此它属于前端

设计把 `x` 定死了语义：**默认 5、范围 1–60 整数秒，只控制文字重算，不控制 Git
freshness；调整后只维护一个计时器**（设计 §4.2 末段）。这条决定了持久化位置，
也决定了 C05 的改动范围：

- 不新增后端命令、不进 `window.json`、不进任何 Rust 设置文件。它和接口缩放、主题
  是同一类偏好，`localStorage` 是**正确位置**而不是妥协：已有先例
  `src/font.ts:18,26` 与 `src/views/settings.ts:239-242`，同样是“非法值拒绝并保留原值”
  的形状（`font.ts` 里已有 clamp）。
  而最贴近的先例是主面板分隔比例那一个（`src/splitModel.ts` +
  `mainPanel.ts` 的 `SPLIT_KEY = "guit.mainSplit"`），它把这类偏好的四件事都做成了
  现成形状，C05 应当照抄而不是重新发明：
  1. 边界常量与 `clamp*` 放在**纯模块**里（无 DOM、无 Git、无样式表），
     因此 `node --test` 能直接测“非法值回默认”——`activityModel.ts` 已经是同一族
     纯模块（§4.5），间隔的 clamp 与它放一起即可，不必再开第三个文件；
  2. `readStored*(raw: string | null)` 单独成函数：空串、空白、非数字都回默认，
     **存进来的值先钳制再使用**，因为“旧版本写的值或人手改过的值”不能让面板进入坏状态；
  3. 键名是 `guit.<camelCase>`；读写各自包 `try/catch`，隐私模式取不到存储时
     面板照常工作（读到默认值），写失败只是下次回到默认；
  4. 设置生效不等于“值变了就重画全部”：那边只写一个 CSS 自定义属性
     （`--main-split`）加 `aria-valuenow`，几何交给样式表。
     这里对应的是“换了间隔就换那一个 interval”，不重排任何列表。
- “只维护一个计时器”约束的是前端：不得为文件区、图表区、活动文本各起一个
  `setInterval`。持有这个 interval 的模块必须在实现说明里点名，并且它的
  `dispose`（同 B03）必须清掉它——否则切换 Tab 或关闭仓库后计时器仍在推进文本，
  这正是 B03 存在的原因，C04/C05 是它的第一个真实用户。
- C01 的 `DEBOUNCE`、最大等待、`POLL_INTERVAL` 保持后端常量，**不接受这个设置值**。
  两个旋钮的不对称关系必须写进实现说明，避免后来者“顺手”把它们接成同一个：
  用户设 60 秒不得让面板的 Git 数据陈旧到 60 秒，设 1 秒也不得变成每秒一次 Git 读。

顺带记录一处本次不涉及、但下一个真正需要后端持久化的设置一定会踩的迁移陷阱：
`main.rs:258-266` 在读 `window.json` 时把 `schema_version != settings_version()`
判成 `settings_invalid`，也就是说**升版本号会让老用户已存的窗口几何整体作废**；
现有新增字段一律用 `#[serde(default)]` 而把 `settings_version()` 保持为 1
（`main.rs:143-160`）。写盘 helper 与 `WindowSettings` 类型耦合
（`write_window_settings`，`main.rs:179`），要复用就得先泛化成按类型写 JSON 的 helper；
另外该文件的校验把“窗口尺寸非法”和“版本不匹配”判成同一种错误，
一个只描述窗口的文件名也解释不了别的偏好，因此届时应当另建具名文件，
沿用 `session.rs:16` 常量与 `session.rs:420` 的拒绝 里 `RECENT_SCHEMA_VERSION` 的“模块内常量 + 不匹配即拒绝”形状。

### 4.2 若某个值真要接到后端环路，生效路径只有两条

`run_loop` 在进入循环**之前**就算好了 `tick` 与 `next_poll`（`watch.rs:74-75`），
而 `supervisor` 把 `DEBOUNCE / POLL_INTERVAL / HEARTBEAT` 三个常量硬编码传进去
（`watch.rs:230-236`）。所以“传一个新 Duration 进去就即时生效”是不成立的：
只有经由已有的 `watch::restart`（`watch.rs:278`）重建 supervisor，或让环路每轮重读
共享值。选择重建还要说明正在进行的有界刷新如何与新旧两个环路交接
（`WatchState` 只保证旧线程在一个心跳内自退，不保证有序）。
按 §4.1，C05 不走这条路；这一段是为了让下一次有人想走时不必重新发现。

### 4.3 活动状态不得挂进快照

`SnapshotView` 是 `publish` 的唯一载荷，而 `publish` 需要一个完整的 `Capture`
（`session.rs:188` 的 `Capture`，其 `PathTable` 在 `model.rs:110`）。把活动状态塞进快照会强制两件事之一：
每次索引变化都配一次 Git 捕获（与 §1.1 的“免 Git 读增量更新”直接矛盾），
或者造一次没有捕获的发布（破坏“快照即一次捕获”的既有不变量，并让 `version`
与文件寻址之间的关系变得可疑）。因此活动状态走**独立事件通道**，载荷直接取设计里
已经定形的 `ActivityView`（设计 §4.1：`sessionId`、`generation`、
`latestModifiedAt`、`observedAt`、`state`、可选显示名与错误原因，
`state` 至少区分 scanning/ready/empty/partial/stale/unavailable），
前端按 `sessionId + generation` 丢弃迟到的旧代次；计时组件不得仅凭
`latestModifiedAt` 为 null 猜原因。

接线点现状：全局 `listen` 只有两条——`repo-refreshed` 与 `watch-status`
（`main.ts:295-296`），后者已经带自己的状态形状。C04 是第三条，
必须落在 B03 的按域订阅上；如果实现时图省事写成又一个全局 `render`，
“静止时计时 tick 不重绘文件列表与图表”这条就自动失效，且现有测试不会报错。

反过来，纯“多久以前”的文本推进不需要后端参与：`observedAt` 一到，
前端按设置值重算文本即可。区分这两类是 C04 的核心：
**索引变了才发事件，时钟推进只改文本。**

### 4.4 活动文本是前端第一处时钟算术，因此要先定形再实现

对现状代码的盘点（`app/src/*.ts` 与 `app/src/views/*.ts` 全量 grep）：

- **没有任何 `setInterval`。** 前端定时器只有三处一次性 `setTimeout`：菜单打开后
  延迟一拍再挂外部点击监听（`dom.ts:202`）、窗口设置 400 ms 合并写入
  （`window.ts:59`）、提交行高亮 950 ms 回落（`history.ts:642`）。
- **没有任何 `Date` 使用**：`Date.now()`、`new Date()`、`Date.parse`、`toLocale*`
  一处也没有。日期一律是 Git 产出的字符串，前端只截断显示
  （`history.ts:535,623` 的 `authorDate.slice(0, 10)`；来源是 `history.rs:18`
  格式串里的 `%aI`/`%cI`）。

三条后果都属于“没有先例可抄”，所以写成契约而不是等着沿用惯例：

1. **C05 的计时器是整个应用第一个周期定时器。** §4.1 要求点名持有者并由它的
   `dispose` 清掉，这条不是形式：仓库里还没有“周期任务随视图生灭”的形状可参考，
   它是 B03 订阅模型的第一处真实用法。若 B03 落地的模型覆盖不了
   “持有一个 `setInterval` 的模块”，C05 就还缺前提，应当回头而不是另造一套。
2. **格式化函数不得自己读时钟。** `activityModel.ts` 与
   `fileModel.ts`/`historyModel.ts`/`railModel.ts` 一样要被 `node --test` 直接
   import（AGENTS.md 的纯模型规则，且不得引入 DOM）。因此年龄必须是对**注入的 now**
   的纯函数（`latestModifiedAt`、`observedAt`、`now` 三个入参），否则夹具测试只能真等秒数，
   也复现不出“多久以前”的边界文案。谁供给 `now` 与谁持有 tick，必须是同一个模块。
3. **两套时钟各有归属，不得混用。** “多久以前”是墙钟差值：文件确实随真实时间变旧，
   休眠或校时让这个数跳大是**正确行为**，不需要“检测休眠”。需要防的是反向混淆——
   C02 的 `stale` 判定是“我多久没拿到证据了”，必须用单调钟；用墙钟相减时，一次向前的
   校时会让刚建好的索引被宣布陈旧。后端对应形状的先例是 `runner.rs:179` 的
   `started.elapsed()`（`Instant`）判超时，而不是任何 `SystemTime` 相减。
   负年龄同样要显式定形：**不得让负数或 `NaN` 到达 DOM**，算术上先夹住；但“夹到 0”之后
   显示什么不是 free choice。验收侧两条都写了：差值按 0 钳制、不产生负数或“刚刚之后”的
   伪值，以及“无负数或‘刚刚修改’伪结果；校准状态明确”。一个来自时钟异常（mtime 晚于
   面板时钟、时钟后退之后）的负差值，对应的**事实是“我们没有看见那次修改”**，
   说“刚刚”是在替一次不存在的修改背书。因此本条按验收一侧定形：
   负差值走独立的“时间不可信”显示分支（§4.5），不借用最小年龄档的文案。
   这里仍沿用 `askpass.rs:446-450` 的保守精神——时间戳在未来时不宣称它旧——
   只是保守的一侧不是“说它新”，而是“不说”。

§4.3 定形了 `latestModifiedAt`/`observedAt` 这两个字段，此处补上它们的类型选择：
跨通道传输用 **epoch 数字**，不用格式化字符串。`types.ts` 里现有日期是字符串
（`authorDate`、`StashEntry.date`），只因为前端从不对其做算术；活动值每 tick 都要算，
用字符串等于把解析塞进那条唯一的纯模型里。格式化后的文字属于 shipped text，
受文案门禁约束。

### 4.5 `activityModel.ts` 的导出形状：先按 `state` 分流，再算年龄

C04 没有先例可抄（前端从不产生“由状态决定读哪些字段”的纯模型），因此把导出面定到
可以直接写测试的程度。约束只有四条，命名可以随实现微调，四条都不能省：

- **一个纯函数入口**，签名 `(view: ActivityView, now: number) => ActivityDisplay`。
  `now` 由持有 tick 的模块注入（§4.4 第 2 条），函数内部不得读时钟。返回值是
  判别联合（携带年龄文本 / 携带原因文本 / 两者都不带），不是 `{ text: string }` 这种
  把分支推回调用方的形状——那会让 `mainPanel` 重新长出 Git 语义。
- **入口的第一件事是按 `state` 决定读哪些字段**，`latestModifiedAt` 为 null 只与
  特定状态同时出现，绝不作为推断依据（设计 §4.1 与 §4.3 末句）。
- **年龄分档边界是具名导出常量**，与 `FILE_ROW_REM` 同一处置：夹具测试直接断言边界，
  实现改一档必须改测试。
- **只有带数字的状态参与每 tick 重算**。`scanning`/`empty`/`unavailable` 的文本
  不随时间变化，tick 到了也不重算它们；tick 不产生 Git 调用（roadmap C04 验收）。

`state` 与显示的关系钉成一张表，实现按它写：

| `state` | 年龄数字 | 必须另外说明的 | 禁止 |
| --- | --- | --- | --- |
| `scanning` | 无 | 正在统计（不得看起来像 `empty`） | 显示上一次会话的值 |
| `ready` | 有：非负差值走分档文本 | —— | 把观察时间当修改时间 |
| `ready` 且差值为负 | 无，走“时间不可信”分支 | 面板时钟与时间戳不一致（§4.4 第 3 条） | 借用最小年龄档文案 |
| `empty` | 无 | 该仓库没有符合条件的工作树文件 | “无变化”“刚刚” |
| `partial` | 有，但标注为已覆盖部分 | 不完整（原因由后端自己的 `stat` 分流得出，不从 stderr 反解，§2.6） | 说成完整 |
| `stale` | 保留最后已知值 | 证据已过期 | 让过期的数字看起来新鲜 |
| `unavailable` | 无 | 不可用的类别（读失败 / 仓库不可识别） | 空白、或退化成 `empty` |

`stale` 一行的两件事分属两个时钟：数字是墙钟算出来的显示值，是否进入 `stale` 由后端
单调钟判定（§4.4 第 3 条）。前端不得自己数秒来决定陈旧，否则刷新失败与文本推进就
混成一条，`ActivityView.state` 失去意义。

既有的连续写入/未来 mtime 夹具（`app/tests/semantic-fixtures.mjs:103`，
`age is a bounded difference and future stamps never read as negative`）只固定了**算术**
一侧：`Math.max(0, now - latest)` 得 0。它没有固定文案，因此也不能被读成
“0 就走最小年龄档”。`ready` 的负差值分支需要 C04 自己补一条断言（同文件形状：
注入 `now`、断言返回的是不带年龄的那一支），否则这条分支在测试上是隐形的。

### 4.6 B03 的订阅形状：C04 的接法按它定形（HEAD 的事实，最初读自并行工作树）

**这一节最初读自尚未提交的并行改动；它现在是 HEAD 的事实**（B03 提交于 `d60f177`，
`app/src/lifecycle.ts`、`app/src/snapshotBus.ts` 与两份夹具随之落地，
该提交零个 `src-tauri/` 文件改动）。落地后在盘上复核过的形状：
`onDispose` / `pendingTeardowns` / `disposeAll` 三个出口，
`SnapshotDomain = "graph" | "refs"` 与 `SNAPSHOT_DOMAINS`，
`graphKey`/`refsKey` 都带 `headState`，`subscribeToDomain` 返回反注册函数，
`domainSubscriptions(domain?)` 与 `publishSnapshot(snapshot | null)`。
这里只定形**接法**，不引用行号（那正是接下来要被改的 `app/tests/` 与视图文件）：

观察到的形状（逐条从 `d60f177` 的代码里读出来，不是推测）：

- `onDispose(task)` 返回反注册函数；`disposeAll()` **后 attach 的先 release**，
  并且吞掉抛错的 teardown；`pendingTeardowns()` 是给探针用的计数。
  视图的用法是在 attach 的那一行旁边登记，例如列宽观察器 `observe` 之后紧跟
  `onDispose(() => watcher.disconnect())`。
- `snapshotBus` 的域是 `"graph" | "refs"`，每个域一个**由快照字段算出的键**，
  键不变就不通知；`publishSnapshot(null)` 表示会话结束，顺手清掉记住的键
  （注释写明“下一个仓库不得继承这个仓库已经看过什么”）。
  订阅按 handler 引用去重，`domainSubscriptions()` 同样是计数。
- 它的第一条夹具钉住的是：“同一内容的更高 `version` 不产生任何读取”——
  **快照单调 `version` 被刻意排除在键之外**。

由此，C04/C05 有四条接法现在就能定死：

1. **活动值不进 snapshotBus 的域。** 域键只能是快照字段的纯函数，而 §4.3 已定形
   活动不挂进快照，因此它在 `DOMAIN_KEY` 里必然没有键可算。活动走自己的一条通道
   （后端 `ActivityView` → 前端订阅），只向 B03 借两样东西：`lifecycle.onDispose`
   负责关掉计时器，以及“身份要在键里”这条规则。
2. **tick 绝不能借道的 fan-out 来实现。** 两条路都是错的：把 `now` 塞进某个键，
   等于每 tick 全量通知（正是 §4.1 要防的“每 tick 重绘完整图”）；不塞，
   则“同一内容的新版本不通知”这条被夹具钉住的规则会把每次 tick 吞掉，
   文本永远不动。年龄文本的驱动源只有计时 tick 与活动通道两处，与快照无关。
3. **计时器的归属有了唯一正确答案。** `onDispose(() => clearInterval(id))` 写在创建
   它的那一行旁边，而不是某个“切换仓库”的分支里。`disposeAll()` 会吞掉抛错的
   teardown 且不发声音，所以登记进去的每一步都必须是不会抛的那种。
4. **泄漏已有现成的两条计数**，C04 不再新增探针接口：反复切页/换仓库之后
   `domainSubscriptions()` 与 `pendingTeardowns()` 要回到同一个数，
   活动自己的订阅数也要跟着可数（同形状的断言，写在 `app/tests/` 里）。
   但这两条计数覆盖不到周期定时器与事件监听，见 §4.9 的三条盲区。

“此刻在不在屏上”这个判断已经有了现成出口，不要在活动这一侧重造。
B03 为 refs 挑选器加的是 `shell.registerOverlay(content, onShow?)` 与
`shell.isOverlayOpen()`（盘上复核：`shell.ts` 里两个出口都在，`main.ts` 用后者
决定“这一轮要不要重读名字”）。按 §4.1 与上面第 2 条，活动文本的 tick 本来就不该被
可见性门挡掉（它不产生读取，只改一行字），所以 C04 更可能的结论是**什么都不接**；
把这条写下来是为了防止实现时顺手加一套自己的观察器——那会变成第二份
“谁在屏上”的判断，而 §4.7 已经说明多一个直接子元素就会动到量出来的区域下限。

还有一处**需要与 B03 的作者对齐**、且会改变 C04 写法的分歧，已经得到了答复。
分歧是：那一版的域键用 `repo.openPath` 作身份，而 A03/B05 的夹具已经证明
“同 HEAD OID + 同分支名”在克隆出来的两个仓库里完全相同；若键仍只到路径为止，
就会出现两套身份——snapshotBus 认为“内容没变所以不通知”，
活动通道认为“这是另一个会话所以旧值作废”。
B03 的记录接受这条，并把身份**判给了 B05 一处定义**：键的身份在 B05 之后升级为一个
会话身份，总线只是使用它；除 `publishSnapshot(null)` 外不应有第二处“会话结束”的判断，
活动通道订阅同一处。它同时补了一个我原先没看到的失败样例：裸仓库与未诞生分支
都只有空 `name` 与空 `oid`，所以键里必须带 `headState`——身份靠快照字段带出来，不能靠猜。
对 C04 的写法只剩一句结论：**活动通道不定义身份，只消费 B05 给的那个会话身份**，
并且它作废旧值的时机必须与 `publishSnapshot(null)` 是同一个时机（否则一个已关闭的
会话仍会把上一仓库的年龄显示在这一仓库上，那正是路线图给 C04 的第一条验收）。

### 4.7 活动文本的落点由“量出来的区域下限”决定

主面板的区域下限不是写死的像素，而是**量出来的**（`mainPanel.ts:76-115`，
上一节的分隔比例同属这套几何）。读下来的规则只有四条，但它们直接决定
活动那一行能不能加：

- 每个区域的根是一个扁平容器：更改区根元素是 `section.view-body.changes-view`，
  它今天的直接子元素就四个——操作横幅、`.file-list`、空状态 `p.empty-state`、
  提交框（由 `createChangesView` 里装配它们的那一次 `element.append(...)` 决定；
  这里不写行号，那个文件正在被并行改动）。因此 list 与区域的同一性比较成立。
- `measureChrome()` 遍历 `region.children`：等于 list 的那个只计“格子数”不计高度，
  其余**直接子元素且 `offsetHeight > 0`** 的算进 chrome，最后加
  `(boxes - 1) * rowGap`。也就是说隐藏的行天然不计高度也不计 gap（这正是
  合并横幅用的机制），而 chrome 变了才重写自定义属性。
- 被观察的对象是“region 本身 + **建立那一刻**它的每个子元素”（`chromeObserver`
  在 setup 时遍历一次 `region.children`）。后来才插入的子元素不会自己被观察到。
- list 是用 `querySelector(LIST_SELECTOR)` 找到的，但排除判断是 `child === list`
  的**同一性比较**，只对直接子元素成立。

因此 C04 的那一行有唯一安全的位置：**在 `createChangesView` 里就建好、作为更改区
的直接子元素存在，之后只改文字或切显示**。三条后果：

1. 放这里，行高被下限自动吸收，界面缩放、横幅出现、提交框拉高都仍按同一条规则
   收敛，不需要为活动文本写任何几何代码。
2. 放到两个区域之外（面板头部、状态条）就**不在 `--region-chrome` 的口径里**，
   下限恰好少一行。B02 记录里被验证过的那条不变量——多种窗口尺寸 × 多种比例下
   `panelScroll=0` 且提交框完整可见——会先在这里破，而**症状出现在提交框上，
   不是出现在新加的那一行上**，事后很难归因。
3. 按需插入（只在某个状态才 `append` 这个节点）是最容易顺手写出、也最难发现的一种：
   它同时踩上“插入的元素不在观察列表里”和上一条的口径问题。要做的是**建一次、
   之后只 retext/切换显示**；隐藏态由 `offsetHeight > 0` 自动排除，不需要额外规则。

顺带一条不属于 C04、但 C04 可能顺手破坏的：不要把 `.file-list` 包进新的容器。
`querySelector` 仍然找得到它，而 `child === list` 从此永不成立，
于是整个列表的高度被当成 chrome——区域下限变成“全部内容”，
面板自己滚动，两半不再同屏。这一条值得在 C04 的自查里，因为它没有任何报错。

### 4.8 事件面没有任何门禁，而它今天恰好是平的

§4.3 定形了活动值不进快照，因此它只能走**后端 emit → 前端 listen** 这条通道。
读下来，这条通道上没有任何一处是被测试保护的，而已有代码里就有一个失败样例：

- 命令面有门禁：`app/tests/ipc-surface.mjs` 要求每个 `generate_handler![]` 里的名字
  在前端以**带引号字面量**出现（注释会被剥掉后再匹配），并且反过来要求每个
  `invoke("...")` 的字面量都有注册。任何一边改名都会让门禁失败。
- 事件面没有对应的检查。本轮按同样的文本口径数了一遍，**并且是在仅本地收敛落地之后
  重数的**（`6d26df5` 删掉了克隆/同步/子模块/凭据那几个 emit）：后端 `emit("...")`
  的名字共 **2** 个，前端 `listen<...>("...")` 的名字共 **2** 个，两边**恰好一一对应**
  （`repo-refreshed`、`watch-status`）。也就是说，这条门禁**今天加上是免费的**：
  它现在就是绿的。而名字对不上时不会有任何东西失败——面板只是再也不更新，
  这与 §2.5 那一族“读不到长得像没变化”的形状是同一个。
  **扫描必须允许 `(` 与字面量之间有换行**：`watch-status` 那四处后端调用全部写成
  `app.emit(\n    "watch-status",\n …`，而 `repo-refreshed` 是单行
  （`watch.rs:246`）。按行匹配的正则（`grep -o '\.emit(\s*"'` 这一类）只会数出
  1 个后端名字对 2 个前端名字，于是这条门禁在**代码没坏的时候报红**。
  能跨行的写法是把整个文件读进来再用 `\s` 匹配（`\s` 含换行），本轮就是这样重数的。
- 载荷类型同样没有共享。`watch-status` 的后端形状是
  `WatchStatus { mode: &'static str, failed: bool }`（`watch.rs:168-173`，
  带 `#[serde(rename_all = "camelCase")]`），前端 `state.ts:98`/`134`/`176` 三处
  接收端却是窄并集 `"none" | "poll" | "events"`，而**中间的桥在 `main.ts:283-284`
  把认不出的值折成 `"events"`**——也就是折成看起来健康的那一档，且那份载荷是就地匿名
  写的 `{ mode: string; failed: boolean }`。线上类型比落地类型宽，桥又朝好的方向失败：
  这条链路上没有任何一处会因为多了一个 mode 值而报错。
  同一段代码也给出了 C04 监听应当照抄的形状：两个 `listen` 都把 `unlisten` 交给
  `onDispose`（B03 的释放登记），并配一句注释说明“只要会话活着后端就在推”，
  所以停止方式是**留着**而不是丢掉。活动事件是第三个住户，没有理由不沿用。

由此对 C01/C02/C04 定三条：

1. **活动事件的载荷必须有共享类型。** `ActivityView` 在 `types.ts` 里声明并被
   监听端 `listen<ActivityView>(...)` 引用，禁止 `main.ts` 那种就地写死
   `{ mode: string; failed: boolean }` 的匿名载荷。年龄与状态由 §4.5 的纯函数分流，
   未知 `state` 值**不得**折进任何已知状态（那是上面那条失败样例的翻版）；
   认不出来就是 `unavailable`，因为“我收到了但不认识”永远不是“一切正常”。
2. **camelCase 是逐结构 opt-in 的。** 后端忘记写 `rename_all` 时 JSON 键是
   snake_case，前端拿到的是 `undefined`，而 §4.4 禁止 `NaN`/缺值参与算术——
   所以夹具要断言的是**键名**，不只是能不能编译。
3. **C02 的提交里带上事件名门禁**，形状照 `ipc-surface.mjs`：扫 `src-tauri/src/*.rs`
   里的 `emit("x")` 与 `src/**/*.ts` 里的 `listen<...>("x")`，两个方向都不许有孤儿。
   它现在就能通过（2/2），因此不存在“先加测试还得先修代码”的负担；
   而活动事件一旦加入，它就是这条面上第一个可能被拼错的名字。

顺带把 C01 的一处既有约束连上：本文 §1.2 要求 Watch 模式自带兜底、并把降级做成可见状态。
若那需要新增 `mode` 值，**同一次提交**要改后端 `WatchStatus`、`state.ts` 的并集、
以及 `main.ts` 里那条把未知值折成 `"events"` 的分支——最后这条现在没有测试会提醒，
只有第 3 条那种按名字配对的门禁能把它带进同一次改动。

### 4.9 新增的读预算探针能证明什么，不能替 C 证明什么

`tools/bench/read-budget.mjs`（随 B03 提交在 `d60f177`）把**构建产物**跑进无头浏览器，
把 Rust 一侧整体换成一个计数桩：它记录页面 `invoke` 了哪些命令、各几次，并统计
`window`/`document` 上的监听数、存活的 `ResizeObserver` 数、待触发的 `setTimeout` 数
与 DOM 节点总数。它断言的四件事里，有两条正是 C 必须保持的形状：

- 内容没动的刷新，除 `refresh_repository` 本身之外**一个域读都不发**，
  只有动过且正在显示的域才重读；
- `stash_list`/`list_remotes`/`pull_default`/`list_worktrees`/`submodule_status`
  被归进 `NEVER_READ`，也就是"没有任何页面会读它们"。

于是 C03 的重枚举与 C01 的溢出补读**只能是快照路径上的一次读**，不能被做成前端
每次刷新主动 `invoke` 的一条命令：一旦那样做，上面第一条立刻红，而这条门禁现在是免费的。

但它是**只看得见前端**的探针，三处盲区要写在这里，免得 C 把它的绿灯引用成别的含义：

1. **事件通道被桩成空操作。** `window.__TAURI__` 的 `listen` 返回一个空函数的
   Promise，`...|listen` 那次 invoke 只回一个 id。所以 §4.8 定下来给活动用的
   emit→listen 那条面在这里**不产生任何计数**，活动监听泄漏它抓不到。
   这一条不是我的推测：B03 的记录把同一件事写在自己的已知缺口里
   （`unlisten` 不会到达 Rust，探针只能证明注册数不增长）。因此 C04 的
   `onDispose(unlisten)` 由**代码位置 + `tests/lifecycle.mjs` 那族断言**保证，
   而"真实关闭旅程"这笔账归桌面阶段，C04 不得引用这个探针声称它已过。
2. **`setInterval` 没有被包装。** 它只替换 `setTimeout`/`clearTimeout` 来数待触发定时器，
   而清点过两次（那一版工作树与 `d60f177` 之后各一次）：前端**一处 `setInterval` 都没有**，
   只有三个短命的一次性
   `setTimeout`（窗口设置保存、`dom.ts` 的一个、历史行闪烁）。也就是说
   C04 的那个周期定时器是**这一列里的第一个住户**：即使它每一次切页都漏一个，
   探针的 `pending timers` 仍会报 `0→0`。所以 C04 不得把"探针绿了"当作自己没有泄漏
   的证据，活动定时器与活动监听的计数要 C04 自己给（同形状的断言写在 `app/tests/`，
   或按 §4.6 第 3 条在创建处 `onDispose(() => clearInterval(id))` 并让登记数可查）。
3. **后端的 git 子进程不在它视野里。** `watch.rs` 的刷新与兜底 tick 在 Rust 里自己
   spawn，前端一次请求都不发。"idle 期间不常驻执行 Git"这条承诺不能引用它结案
   （见 [A02 基线记录](08-gate-baseline-a02.md) 第 7.1 节同一行）；后端侧若要一个
   计数口径，需要新增的是 spawn 计数，而不是把期望压给这个文件。

另外，它需要浏览器和已构建产物，因此不进 `npm run test:fixture`——C 阶段的"每次提交都全绿"
不包含它，得单独跑。还有一处容易误读：`NEVER_READ` 只断言"没人读"，不断言"命令不存在"。
退出清单把 `pull_default`/`list_remotes` 从注册表移除后，桩里那张 table 仍留着它们，
这条断言会继续绿；真正被移除动作触发的是 `ipc-surface.mjs`。

## 5. C01 环路原型实测（一次性 /tmp crate，非交付代码）

在改动 `watch.rs` 之前，先用 notify 8.2.0 + 真实 inotify 事件验证“quiet 或最大等待取先到者”
的环路是否成立。夹具：临时目录递归监听，后台线程按固定间隔写文件，统计捕获次数与
**首个待处理事件到捕获之间**的最差延迟。同一主机同一构建（debug）实测：

| 场景 | 写入节奏 | 捕获次数 | 最差“首事件→捕获” | 说明 |
| --- | --- | --- | --- | --- |
| 连续风暴 | 每 20 ms 一个文件，约 5.6 s | 6 | **1.0002 s** | 等于 `MAX_WAIT`；现行实现此场景 0 次捕获 |
| 风暴 + 队列上限 4 | 同上 | 4 | 1.0006 s | 114 次溢出合并，域信息未丢，捕获仍按上界发生 |
| 单次写入后静默 | 1 个文件 | 1 | **250.1 ms** | quiet 路径未被最大等待改动破坏 |

由此确定 C01 的三条实现约束：

1. 待处理为空时只等心跳/轮询；有待处理时唤醒时间取
   `min(quiet 剩余, max_wait 剩余, 心跳)`，两者都不满足不得捕获。
2. 触发后清空队列并重置两个时间戳，使风暴期间的捕获节奏稳定在每 `MAX_WAIT` 一次；
   捕获自身耗时由 `session.rs` 的 leader/rerun 门吸收，环路不再叠一层节流。
3. 溢出时把丢掉的条目按数据域合并回队首并标记“需要重新核对”，不得当作无事发生。

原型只为拿到这三条结论与延迟量级，不进入仓库；正式实现连同“连续事件不饿死刷新”的
测试一起落在 `watch.rs`（阶段 C）。

落地时还有两处形状约束，避免测试被迫等真实秒级时间：

4. `max_wait` 必须像 `debounce`、`poll_interval`、`heartbeat` 一样是 `run_loop` 的**入参**
   而非模块常量（`watch.rs:65-73`）。否则新测试只能真等 1 s，与现有环路测试
   用 10–80 ms 计时的强度（`watch.rs:333-424`）不一致，也容易在慢机器上抖。
5. 把通道元素从 `()` 换成事件值，直接受影响的驱动点是
   `watch_events_debounce_into_a_single_fire` 里的 `tx.send(())`（`watch.rs:353-355`）；
   其余三条环路测试只建通道不发送，随签名改类型即可。这是预期的连带修改，不是回归。
   但 `watcher_delivers_real_filesystem_events`（`watch.rs:452-459`）目前只断言
   “收到一个东西”，改类型后应顺带断言它携带的路径与种类，否则这条测试对新契约
   毫无约束力。

## 6. 未决事项

- §1.2 的监听失效形状全部在 Linux/inotify 上测得。notify 在 Windows 与 macOS 走的是
  另外的后端，`watch()` 是否同样按路径去重、`unwatch()` 的错误形状如何、递归覆盖是否
  也在事件之后才建立，均未验证；跨平台实现前不得把本节结论当作三平台共同的契约。
- §1.4 的队列数值已按实测事件率定下（1024 条通道容量 + 同量级去重路径上限，
  解释方式是“新建文件：每次写入 4 条事件、2 条非 Access”）。§1.4 后面那张追加型负载的
  表把这条解释限定了范围：同一比率在那种负载下不成立，且那两个上界的余量要按各自形状给
  （1024 条在 25 次/秒的追加下是 41 s，在全速新建下是 6 ms）。当时跟着这条限定记下、
  本轮又补测掉的一件事是**编辑器保存**：比率是每次保存 5–6 条事件、1–2 条新路径，
  而深度那一维的答案是 0（§1.4 末那张表与它的四条后果）。其中“去重路径会被临时名吃满”
  那一条改变了上界的解释方式，所以 §1.4 给那两个数值的理由不再是“按写入次数换算”，
  而是“按窗口内仍然存在的候选路径条数换算”——合并集必须按种类淘汰，不得只进不出。
  仍待实现确认的是：真实仓库里的原子保存还会**附带**哪些非候选路径（锁文件、`.swx`、
  构建输出），以及这两个数值在 Windows 的读取后端上对应什么比率——比率和数值都不得
  当作跨平台常数。
- Watch 模式兜底刷新用哪个间隔（复用 `POLL_INTERVAL`、按心跳计数、还是新增具名常量）
  是实现要选的，本文只固定“必须存在且不得依赖 `Err`”。选定后要在实现说明里写明该间隔，
  并回答它带来的代价：兜底刷新在无变化的仓库上仍会付一次 `git status`
  （沿用 `--no-optional-locks`，`watch.rs` 环路原有的 Poll 分支已经是同一形状），
  这是把“面板永不更新”换成“每个兜底间隔一次可忽略的读”，需要显式记录而不是当作免费。
  这条交换成立的前置条件已经实测（§1.3 的那张表）：一次无变化的捕获产生 **0 条**非 Access
  事件，所以新增的节奏不会自喂；但它依赖 `--no-optional-locks` 与 `Access(_)` 整类丢弃
  同时保持现状。
  §3 已经让同一个 tick 兼做“仓库外忽略来源”的 metadata 核对，因此选定间隔时要按
  **两处用途共同的代价**记录，并且不得为此再新增第二个间隔。
- 活动枚举的上限形状已按 submodule 视图的先例定为“模块内具名常量 + 32 MB 档”（§2.2）；
  具体常量名与注释随实现落地后，需要在 `docs/known-limitations.md` 的 output bounds 一节
  补一条同等强度的记录，不得只留在代码注释里。
- Windows 的路径大小写/分隔符与符号链接语义、`~` 不展开时的默认忽略路径均无实测；
  §2.4 的字节契约也只在 Linux/UTF-8 文件系统上测得，Windows 下名字如何到达
  `OsString`（WTF-8 形态）与 Git 的输出编码都还是未知。
- `status_output` 把 stderr 一并交出已不是“要不要改”的问题：影响面清点是两个生产调用点
  （`session.rs:205` 快照、`write.rs:885` 写前 recheck，§2.6 末）。剩下未决的是
  **recheck 一侧如何处置非空 stderr**——把它当作“绑定事实不可信”直接拒绝写入，
  是当前 fail-closed 形状的自然延伸，但会让一个只读不动无关目录的仓库失去写入口。
  活动索引那侧按 §2.5 的表分状态已经定形，快照那侧的处置与它是同一次改动。

## 7. 复现方式

本文表格中的每条 Git 行为都可用一次性夹具复现：临时目录内 `git init`，
设置 `GIT_CONFIG_NOSYSTEM=1`、`GIT_CONFIG_GLOBAL=<夹具内文件>`、`GIT_TERMINAL_PROMPT=0`、`LC_ALL=C`，
分别构造：已跟踪后删除的文件、未提交的 `.gitignore`、`.git/info/exclude`、
普通未跟踪目录、含自身 `.git` 的嵌套目录、`update-index --cacheinfo 160000,<oid>,mods`
得到的 gitlink（本轮补测：直接 `git add -A` 提交一个嵌套仓库同样得到 mode `160000` 项，
且 `--cached -z` 输出不带斜杠）、`ln -s` 指向仓库外的链接，然后比对
`ls-files --others --exclude-standard[-z]`、`ls-files --cached`、`ls-files --cached --stage -s`、
`check-ignore -v`、
`config --show-origin --get core.excludesFile` 的输出。
§2.4 的名字夹具：同一目录里放 `plain.txt`、`中文.txt`、`quo"te.txt` 与
zsh 的 `$'bad\xff.txt'` 产生的非法 UTF-8 名，比对 `ls-files --cached` 与
`ls-files --cached -z | od -An -c`，再用一次性程序分别对原始字节与
lossy 之后的字节 `stat`（本轮用 Python 做的这一步：前者成功、后者
`FileNotFoundError`）。非法字节名只在 Linux/UTF-8 文件系统上有意义，
同一夹具在 Windows 上根本构造不出来。
§2.5 的权限夹具：一个仓库里放 `sub/`（已跟踪文件改一次、再放一个新文件）与
`ok/`（一个新文件），提交后 `chmod 000 sub`，分别跑 shipped 的 `status` 形、
`ls-files --cached -z`、`ls-files --others --exclude-standard -z` 并**分开看
stdout 与 stderr**（只看 stdout 会得出“干净”的错误结论）；
再单独 `chmod 000 .git/objects` 看 128 那一支。清理时先 `chmod 755` 再删目录。
§2.6 的三条补测用同一夹具接着做：`chmod 000 sub` 后同一条命令分别以默认语言和
`LC_ALL=C` 各跑一次并**比字节数**（zh_CN 79 B、C 90 B，两行、第一行无 `warning:` 前缀），
这是“只能判空、不能读文本”的根据；再 `chmod 000 <单个已跟踪文件>`（目录保持可读）
看 rc=0 且 stderr 为空、该项以 `.M` 出现，与 `chmod 000 .git/index` 看 rc=128。
mtime 索引的三项成本用一次性 Rust 原型测得（临时目录下 `cargo run`，随进程删除夹具，
不是交付代码）：10 次“两次 `ls-files` + 逐项 `symlink_metadata`”重建、200 轮“取最大后删除”、
1000 次“取最大后写回同一项”。§3 那三条“不监听仓库外路径”的数字来自三条只读命令：
`cat /proc/sys/fs/inotify/max_user_watches`、`cat /proc/sys/fs/inotify/max_user_instances`、
`find "$HOME" -maxdepth 2 -xdev -type d | wc -l`（本机 65536 / 128 / 515），
以及 `git config --global --get core.excludesFile` 与对 `$HOME/.config/git/ignore` 的
`ls -ld`（本机：前者未设置、后者存在）。这两项都不写任何文件，也不需要夹具。
§4.6 与 §4.7 不是测出来的：它们的依据是前端代码本身（未提交的并行改动、
`mainPanel.ts` 的量下限那一段），复现方式就是去读那两处，
因此这两节是三份记录里最容易随时间失效的，落地前必须复核而不是照抄。
§4.8 那两个名字（“两侧各 2 个且一一对应”，`6d26df5` 之后重数；在那之前是 7/7）来自一次
文本扫描（Python：对 `src-tauri/src/**/*.rs`
取 `\.emit\(\s*"([^"]+)"`、对 `src/**/*.ts` 取 `listen(?:<[^()]*>)?\(\s*"([^"]+)"`，
比集合差）。两个正则里的 `\s` 必须能吃到换行，这不是风格：后端 `watch-status` 那几处把
字面量写在 `emit(` 的**下一行**，按行匹配的工具（`grep -o '\.emit\(\s*"'` 那一类）
会数出后端 1 个、前端 2 个，于是这条门禁在代码没坏的时候报红——本轮先用按行的写法数过，
就是这个假失败。两个正则也都只认字面量，因此**这条数只在“两侧都写字面量”这个前提下成立**：
任何一个名字改成变量拼接，扫描就看不见它，2/2 会变成假平的对称。C02 若真要加这条夹具，
得按 `ipc-surface.mjs` 的做法先剥注释、再在夹具里断言“扫出来的数量不为 0”
（那个文件正是用“解析出的命令数必须 >50”来防止解析器退化后让所有断言空过）。
阶段 C 实现时应把这些断言固化为 `app/tests/` 下的夹具测试。

§1.2 与 §1.3 的监听形状由同一原型目录里另外两个 bin 测得（依赖 `notify =8.2.0`，
夹具建在 `/tmp` 下、进程退出前自删）：`dead_watch` 依次跑“监听根删除并重建”
“子目录删除并重建”“`watch()` 错误形状”“git 形态目录里 git 自己的写入”；
`rearm` 依次跑“对同一路径重复 `watch()`”“`unwatch()` 后重听”“根目录消失后靠定时重建恢复”
“子目录重建后的三种补救形状”。复现要点是**每一步之间留 drain 窗口**：
`dead_watch` 场景 2 与 `rearm` 场景 D 的差别只在重建后是否立刻写入，
这正是“递归覆盖在事件之后才建立”这条结论的来源，写成固定 sleep 的测试会把它抹平。
§1.4 的事件率与饱和代价来自同一 crate 的 `queue_rate`：每个窗口用**新的扁平目录**，
监听后 sleep 300 ms 并把注册期间的事件全部丢弃，再启动写入线程，消费者在窗口内一次都不读。
早期版本把 settle 放在写入启动之后、且收尾有一段不受停止标志控制的复写，
结果各窗口互相污染（同一夹具曾读出 140/60 与 76/26 这类不一致的数）；
改成上述形状后四种节奏稳定收敛到 4/2/1 每条写入。饱和一侧是独立函数：
填满 `sync_channel` 后计时一万次 `try_send`，与容量大小无关。
§3.1 的命令形状用一次性 Python 探针测得（临时目录建夹具、脚本退出时删除，
不是交付代码）：50 个目录各 1000 个已跟踪文件，一次提交；再往同一批目录各写 40 个
未跟踪文件；`.gitignore` 与它隐藏的 1000 项目录在同一次提交里。每条命令在同一进程内
跑 7 次取最好，并逐项比对 stdout 的字节路径集合。
**顺序那条结论要单独用小夹具看**：50k 夹具只能证明整条流恰好切换一次类别，
一个 7 项的仓库才看得清是哪一段在前（未跟踪段在前、已跟踪段在后，两段各自有序）。
本轮排除两条早先记下、不得再被引用的数：一条 16 ms 来自一行被 shell 折坏、
把 `--others --exclude-standard` 当成单个参数传下去的命令（Git 报“未知选项”）；
另一次所谓“被忽略的目录”里那个 `sub/.gitignore` 其实从未创建，
它测的是普通目录而不是忽略。写下这两条是为了让重跑的人不再把它们当作本文任何数值的出处。

§4.9 那三条盲区不需要新夹具，一次读文件加两条 grep 就能复核：
`grep -n 'setInterval' tools/bench/read-budget.mjs` **无命中**（它只替换
`setTimeout`/`clearTimeout`），`grep -rn 'setInterval' app/src` 同样**无命中**
（前端当时一处周期定时器都没有，所以 C04 会是那一列的第一个住户）；
事件被桩成空操作则写在同一个文件的 `__TAURI__` 那一行与 `invoke` 里
对 `|listen` 后缀的分支上，直接读得到。

§3.2 用三段一次性 Python 探针测得（夹具在 `tempfile.mkdtemp` 下、脚本退出即 `rmtree`，
不是交付代码）：九形状比对、外部忽略源六次读数、目录项 mtime 一节。
比对一律在字节上做大集合相等（`set(bytes)`），每条命令都经 `cwd=仓库根` 运行，
`-c core.excludesFile=<夹具内的文件>`，并显式剥掉 `GIT_DIR`/`GIT_WORK_TREE`/`GIT_CONFIG_GLOBAL`
——不剥的话本机那份全局忽略会混进读数。两处**先失败后更正**的写法要留在这里，
免得重跑的人再把它们当作结论的出处：

- “`.git/info/exclude` 追加一条规则”那一步在第一次运行时**什么也没改变**，
  因为那两个文件已经被全局模式忽略过了。把夹具改成每个源各配一个只有它能匹配的文件名，
  这一行才第一次真正测到 info/exclude。
- “根 `.gitignore` 自身未跟踪”那一步在第一次运行时写作创建了一个字面名为
  `untracked.gitignore` 的文件，Git 自然不把它当忽略源，于是那一行当时测的是
  “多一个普通未跟踪文件”。改成真正写 `.gitignore` 之后，`brandnew.gen` 才在下一行消失。
  （这与 §7 先前排除的那个 `sub/.gitignore` 从未创建是同一类错误，本轮的嵌套那行
  是先确认 `sub/.gitignore` 出现在 `--others` 里、再确认 `sub/deep.gen` 不在。）

§1.3 的那张表和 §1.4 后四条节奏的事件读数由另一段一次性 Python 探针测得（同样在
`tempfile.mkdtemp` 下建夹具、结束即 `rmtree`，不是交付代码）。它不碰任何仓库代码：
监听侧直接复用**已经构建好的** `app/src-tauri/target/debug/examples/watch_probe`
（只依赖 notify 的诊断 bin，按行打印事件种类与文件名），Python 侧给每一行打到达时间戳。
三条读法上的约定要写下来：

- 时间列是“notify 把事件交给回调之后”的间隔，不是内核时间戳；那个 bin 每行 flush，
  所以管道不改变顺序。种类过滤在 Python 侧重复了 `refresh_worthy`（只丢 `access`），
  因此“非 Access”这一列与环路真正会数到的那一类对齐。
- 捕获那一组用 `repo::status_output` 的逐字参数，`HOME` 指向夹具目录并剥掉全部 `GIT_*`。
  制造“索引 stat 缓存过期”用 `os.utime` 把一个已跟踪文件的 mtime 推到未来，
  然后**先等 2 s 让监听静默**再开始计数——不隔这一步，那一行数的是 utime 自己那两条事件，
  而不是捕获的。
- 该 bin 递归监听仓库根（含 `.git`），比 `watch_targets` 的三个目标略宽（不做去重）；
  文件系统是 tmpfs；它是 debug 构建。这三点都只影响绝对数值，不影响“有无事件”与
  “间隔是否小于 debounce”这两类结论——后者才是那两张表用到的。
§3.3 与 §2.2 末那张截断表由三段一次性 Python 探针测得（`tempfile.mkdtemp` 建夹具、
结束即 `rmtree`，剥掉全部继承的 `GIT_*` 并把 `HOME` 指向夹具目录，不是交付代码）：
`--stage` 那一条在同一仓库里逐字节比对四种命令（`--others --exclude-standard`
带与不带 `--stage`、`--cached --others --exclude-standard` 带与不带），
可伪造的那个文件名要用 `open(..., "wb")` 写——它的名字里有 TAB，是合法文件名字节。
两条**先测出错、后来才修正**的数必须留在这里，免得被当作本文任何结论的出处：

- 第一次截断探针用**等长**文件名（14 字节），于是每个 17 字节的记录边界都落在同一个
  偏移上，测出“0 个切点落在记录中间”。这个 0% 不是 Git 的性质，是夹具的算术巧合，
  已被排除。换成名字长度随序号变化（`t%04d` + `a" × (i % 23)`，未跟踪侧同理）之后，
  94.4% 的切点落在记录中间——**任何**关于截断形状的结论都必须用后者那种夹具来测。
- 同一轮第一次跑 `--stage` 比对时，把“未跟踪项也是裸路径”误读成“输出没变化”，
  原因是那次只比了字节长度没比条目数。按条数拆开看才有 §3.3 表里那行 2 条 vs 3 条。

顺序（未跟踪段在前）在两个独立夹具上方向一致：等长那一个 50% 切点留下 20,000 条全部
未跟踪、0 条已跟踪；变长那一个留下 3,000 条未跟踪 + 158 条已跟踪。这一条性质也是 §3.1
用小夹具（7 项、类别序列 `oooccccc`）读出来的；`--cached`/`--others` 两个 flag 的书写
顺序不改变输出段序（两种顺序逐字节相同），所以实现不能靠调 flag 顺序来控制它。
§1.4 末那张“保存形状”表由两段一次性 Python 探针测得（`tempfile.mkdtemp` 下建夹具、
结束即 `rmtree`，不是交付代码），监听侧仍复用**已经构建好的**
`app/src-tauri/target/debug/examples/watch_probe`，所以全程没有 `cargo` 调用、
不碰共享工作树的 `target/` 锁。三段读法上的约定：

- 每段先 settle 400 ms 再从 `mark` 起算，收尾等 600 ms 把最后一批事件收进来；
  计数只取 `mark` 之后的行，种类过滤在 Python 侧重复了 `refresh_worthy`（只丢 `access`）。
- “事件里的路径条数”这一列依赖**夹具内文件名全局唯一**（`f0000`/`d0000`/`tmp-00042-zzz…`），
  因为那个 bin 只打印 basename。深目录那一行用同样的唯一命名，否则两个目录里的同名文件
  会被折叠成一条路径，深度这一维就被测成“路径更少”这种假结论。
- `modify-name` 每次保存恒为 3 条是**这个 bin 的形状**（notify 把 rename 拆开递出），
  不是内核事件数；换成读 inotify 原始队列会看到另一种条数。本文用的是环路真正数到的那一层，
  所以这张表的条数可以直接用于“每次保存产生几条会触发刷新的输入”。
§3.1 末那四种下发用同一类一次性 Python 夹具测得。**子模块必须手工搭**：
写 `.gitmodules`、在子目录里 `git init` 并提交，再用
`update-index --add --cacheinfo 160000,<oid>,mods` 把 gitlink 放进索引。
`git submodule add file:///…` 会被 Git 默认的 `protocol.file.allow=user` 拒绝
（实测 `fatal: transport 'file' not allowed`），而为了搭一个读取形状的夹具去放开那条
传输策略，正好把本文要避免的“下载”带进了测量现场。gitlink 与真子模块同时放进一个夹具，
是因为 `submodule.recurse` 这一维只有在这两种项都在场时才可能被观察到差别。
